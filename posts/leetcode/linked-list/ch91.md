# LRU 缓存（146. LRU Cache）

## 题意

设计一个满足 LRU（最近最少使用）淘汰策略的缓存：

- `LRUCache(int capacity)`：以正整数容量初始化。
- `int get(int key)`：key 存在返回 value，否则返回 -1。
- `void put(int key, int value)`：key 存在则更新；不存在则插入，超出容量时**淘汰最久未使用**的 key。

`get` 和 `put` 都必须平均 O(1)。

```
LRUCache c(2);
c.put(1, 1);   // {1=1}
c.put(2, 2);   // {1=1, 2=2}
c.get(1);      // 返回 1，1 变最近使用
c.put(3, 3);   // 淘汰 2，{1=1, 3=3}
c.get(2);      // 返回 -1
c.put(4, 4);   // 淘汰 1，{4=4, 3=3}
c.get(1);      // 返回 -1
c.get(3);      // 返回 3
c.get(4);      // 返回 4
```

约束：`1 <= capacity <= 3000`，`0 <= key <= 10⁴`，`0 <= value <= 10⁵`，`get`/`put` 总调用次数至多 `2×10⁵`。

---

## 思路：哈希表 + 双向链表

两个需求拆开看：

- **O(1) 查值**：只有哈希表能做到。
- **O(1) 维护"最近使用"顺序**：每次访问把节点移到头部、淘汰取尾部，双向链表天然支持，而且 `std::list::splice` 移动节点是 O(1) 且不拷贝元素。

合起来：`unordered_map<key, 链表迭代器>` 负责 O(1) 定位，双向链表负责 O(1) 调序。哈希表里存**迭代器**而不是值，这样拿到迭代器后既能读写 value，又能直接 splice 移头，一步都不用找。

## 解法：std::list + splice

```cpp
class LRUCache {
public:
    LRUCache(int capacity): cap(capacity) {
        // 预留哈希表容量，避免后续扩容
        m.reserve(cap);
    }

    int get(int key) {
        auto it = m.find(key);
        if (it == m.end()) return -1;          // key 不存在，返回 -1
        moveToHead(it->second);                // 标记为最近使用
        return it->second->second;             // 返回 value
    }

    void put(int key, int value) {
        auto it = m.find(key);
        // 情况1：key 已存在，更新 value 并移到头部
        if (it != m.end()) {
            it->second->second = value;        // 更新节点中的 value
            moveToHead(it->second);            // 标记为最近使用
            return;
        }
        // 情况2：缓存已满，淘汰最久未使用的尾部节点
        if (lst.size() == cap) {
            int lastKey = lst.back().first;    // 取出尾部节点的 key
            lst.pop_back();                    // 删除链表尾部
            m.erase(lastKey);                  // 同步删除哈希表项
        }
        // 情况3：插入新节点到头部
        lst.push_front({key, value});
        m[key] = lst.begin();                  // 记录其链表位置
    }

private:
    using ListIter = std::list<std::pair<int,int>>::iterator;

    // 将指定节点移到链表头部，标记为最近使用
    void moveToHead(ListIter it) {
        lst.splice(lst.begin(), lst, it);
    }

    int cap;                                   // 缓存容量
    std::list<std::pair<int,int>> lst;         // 双向链表：头部最新，尾部最久未使用
    std::unordered_map<int, ListIter> m;       // key -> 链表节点迭代器
};
```

---

## 核心理解

### 1. 为什么必须用 list 而不是 vector/deque

LRU 的每次访问都要"从中间摘一个节点插到头部"。`vector`/`deque` 做这件事是 O(n) 搬移，而且迭代器会失效；`std::list` 的 `splice` 只改几个指针，O(1)，并且**splice 之后指向该节点的迭代器依然有效**。最后这条性质是整个设计成立的前提：哈希表里存的迭代器在移头之后不用更新。换任何一种"迭代器会失效"的容器，这套写法立刻崩。

### 2. get 也是"使用"

LRU 的语义是"最久未**使用**"，读也算使用。所以 `get` 命中后必须 `moveToHead`，漏了这步，淘汰顺序就错了：一个被频繁读取的热 key 会被当成冷 key 淘汰掉。同理 `put` 更新已存在的 key 也算使用，也要移头。

### 3. 淘汰是链表和哈希表的联动

淘汰尾部节点要做两件事，顺序不能乱：先 `lst.back().first` 取出 key，再 `pop_back()`，最后 `m.erase(lastKey)`。先 `pop_back` 再取 key 就是悬垂访问；漏掉 `m.erase`，哈希表里就留下一个指向已销毁节点的迭代器，下次 `get` 命中它就是未定义行为。

### 4. 另一种常见写法：手写节点 + 哨兵

题解区更常见的版本是自己定义 `Node{key, val, prev, next}`，配 head/tail 两个哨兵节点，`removeNode` + `addToHead` 手动改指针。语义完全一样，但代码量是这里的两倍。面试时 `std::list` 版足够快也够干净，手写版的价值只在于展示你理解底层指针操作。

## 踩坑点 / 注意点

- ❌ **get 漏掉移头**。编译能过、小数据能过，但热 key 会被误淘汰，LRU 语义直接错。
- ❌ **淘汰顺序错**。必须先取 key 再 `pop_back`，且 `m.erase` 不能漏，否则哈希表残留悬垂迭代器。
- ❌ **put 已存在 key 走了插入路径**。会插入重复 key 还触发多余淘汰；必须先查哈希表分流。
- ⚠️ **`lst.size() == cap` 是有符号/无符号比较**。`size()` 返回 `size_t`，`cap` 是 `int`，`-Wsign-compare` 会警告；这里 cap 恒为正所以无害，但严谨写法是 `(int)lst.size() == cap` 或把 cap 声明为 `size_t`。
- ⚠️ **`m.reserve(cap)` 只是优化，但背后有个值得知道的点**。`unordered_map` rehash 会使**指向哈希表自身的迭代器**失效，但元素的指针/引用不失效，存进去的 value 更是会被安全拷贝。这里哈希表存的是 `list` 迭代器（作为 value），rehash 只是把这个 value 搬到新桶，`list` 节点本身纹丝不动，所以设计是安全的；reserve 纯粹是省掉多次 rehash 的时间。
