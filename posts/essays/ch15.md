# JSONL：日志文件为什么爱用"每行一个 JSON"

最近在看一个 agent 项目的日志模块，它的会话记录文件是 `.jsonl` 后缀的。JSONL 是 JSON Lines 的缩写，意思就一句话：每行一个 JSON 对象。

## 长什么样

拿这个项目里的日志文件（`src/core/logger.ts` 写出来的那种）举例，一个 `.jsonl` 文件内容是这样的：

```jsonl
{"ts":"2026-09-17T10:00:01.000Z","kind":"user","summary":"帮我改一下登录逻辑"}
{"ts":"2026-09-17T10:00:03.000Z","kind":"tool_call","summary":"tool: read_file src/auth.ts"}
{"ts":"2026-09-17T10:00:08.000Z","kind":"assistant","summary":"已经修改了 login() 的校验逻辑"}
```

注意它不是这样：

```json
[
  {"ts": "...", "kind": "user"},
  {"ts": "...", "kind": "tool_call"}
]
```

后一种是一个 JSON 数组，得整个文件读完才能解析。JSONL 不一样：每一行单独拿出来都是合法 JSON，但整个文件不是。

## 为什么日志爱用它

关键在写入端的两行代码：

```ts
this.stream = fs.createWriteStream(this.filePath, { flags: 'a' });  // 追加模式
this.stream.write(JSON.stringify(entry) + '\n');                    // 每条事件一行
```

相比写一个大 JSON 数组，好处有三：

- 追加友好：每条新事件就是往文件末尾加一行，O(1) 完成。如果是 JSON 数组，每次追加都要先读文件、删掉结尾的 `]`、插入新对象，文件越大越慢。
- 崩溃安全：程序中途崩了，已写入的每一行都是完整合法的 JSON，只损失最后没写完的那条。数组格式崩在中间，整个文件解析失败。这正好对应这个项目 `ARCHITECTURE.md` 里写的"crash-safe：所有状态每步落盘"。
- 可以流式处理：复盘的时候用 `grep`、`awk` 逐行过滤就行，比如 `grep '"kind":"tool_call"' session-xxx.jsonl`，不用把整个文件加载进内存解析。

代价也有：整个文件不是一个合法的 JSON，要做聚合统计得用支持逐行解析的工具，或者 `jq --slurp` 先把所有行读成数组。

## 不只日志：数据集也一样

之前做智驾训练数据的时候，数据集也大量用 JSONL。道理是同一组：

- 一条样本一行，标注 pipeline 每产出一批新数据，往文件末尾追加就行，不用动已有内容。
- 训练读数据天然是流式的，逐行读、逐条喂，几百万条的文件也不用整个加载进内存。
- 某一行写坏了，最多损失那一条样本，剩下的照常用。要是整个数据集是一个 JSON 数组，一个字段写崩，整份数据就都解析不了了。
- 抽查、过滤、统计行数，`head`、`wc -l`、`grep` 直接上，不用写解析脚本。

日志和数据集看着是两个领域，需求其实一样：量大、追加写、要扛得住中途出意外。

## 小结

高频写、只追加、崩溃不能丢已记录的内容，这三个条件凑齐，JSONL 就是标准答案。这个项目里 transcript 用它落盘，是很自然的选择。
