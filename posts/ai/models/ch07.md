# 推理模型的思维链：展示与回灌是两个独立问题

## 1. 前言

最近在写一个 VS Code 插件的 LLM 流式客户端，接 DeepSeek 的 deepseek-reasoner。解析 SSE 流的时候遇到一个字段：模型的输出拆成两部分，`reasoning_content` 和 `content`。前者是思考过程，后者是正式回答。

当时的直觉是把思考过程也存进对话历史，下一轮请求一起发回去，看着挺完整的，舍不得扔。查了一圈各家 API 的文档才发现这里有讲究，而且各家的规矩正好相反。这篇文章把查到的结论整理一下。

## 2. reasoning_content 是什么

DeepSeek-R1 这类推理模型，回答之前会先输出一大段分析过程，然后才给正式回答。API 的流式响应里，这两部分是分字段下发的：

```jsonc
// 流式 chunk 的 delta 长这样
{ "delta": { "reasoning_content": "用户问的是缓存失效，先想 invalidate 的调用方……" } }
{ "delta": { "content": "这个问题的根因在 store.ts……" } }
```

普通模型没有第一个字段。所以对客户端来说，解析逻辑要多处理一路流，展示层也多一条「思考」轨道。

## 3. 各家对「回灌」的规矩正好相反

所谓回灌，就是把上一轮的某些内容追加进对话历史，下一轮请求再发回给模型。多轮对话里，content 肯定要回灌，否则模型没有记忆。reasoning_content 要不要跟着回灌，各家答案不一样。

**DeepSeek、Kimi、Qwen（QwQ）、智谱这一圈 OpenAI 兼容网关：明确不回灌。** 文档里写了不要把 reasoning_content 放回 messages，服务端会忽略，有的直接报错。这些厂商把思维链当展示产物，明文全给你看，看完就完了。

**Anthropic Claude、OpenAI Responses API、Gemini：必须回灌。** Claude 的 thinking block 带加密签名，带工具调用的多轮对话里，assistant 消息少了这个 block 直接 400。Gemini 的 thought signature 同理，少了会断掉函数调用的连续性。OpenAI 的 Responses API 返回加密的 reasoning item，也要求带回。

也就是说，同样一个「思考过程」，一边要求扔掉，一边要求必须带着。写客户端的时候按一家的规矩写死，换一家就是 bug。

## 4. 展示和回灌是两个独立的维度

一开始我以为这两件事是一回事，给你看就不用回灌，不给你看才需要回灌。把厂商填进 2×2 表格就发现不对，四个象限都有实例：

| | 必须回灌 | 不回灌 |
|---|---|---|
| **给你看原文** | Claude（明文 thinking block，原样带回，签名验证） | DeepSeek / Kimi（明文全给，展示完就扔） |
| **不给看原文** | OpenAI Responses（加密 reasoning item，必须带回，但内容读不了） | OpenAI o 系列 Chat Completions（只给摘要或不给，也没东西可回灌） |

Claude 在左上角，它把思考明文给你看，同时要求你必须回灌。单看「展示」这个维度推不出任何结论。

真正的分界线是厂商把思考当成什么。当成**状态**，它就是连续性对象，回灌义务跟着走，给不给你看是另一件事。当成**产物**，它就是一次性输出，展示是它的全部使命。回灌派的回灌对象也都做成了不透明块，签名或加密，你只能原样搬运，不能读也不能改。这样既保住了推理状态的连续性，又不暴露原始思维链。

## 5. 为什么思考有时是「状态」

推理模型做 agent 任务时，一轮的完整流程是：思考，调工具，看结果，接着想。「接着想」需要之前的推理状态，否则第二轮思考从零开始，长任务里前后决策容易矛盾。Claude 和 Gemini 要求回灌签名块，为的就是这个连续性。

DeepSeek 阵营的选择是每轮重新想。代价是多轮工具任务里推理状态不连续，好处是协议简单，不用搬运签名块。两种取舍都成立，看厂商想优化什么。

## 6. 思考是计费资源

推理模型带来一个新的认知，准确率不只靠更大的模型，也可以靠更长的思考换。同一个模型，想 500 token 和想 5000 token，在难题上的表现差距明显。这个方向叫 test-time compute。

工程上的直接推论：

- reasoning token 按 completion token 计费，一次深度思考的回答，费用大头可能是你不回灌的那部分。
- 简单问题也想 30 秒就是浪费，这叫 overthinking。对应的解法有 budget forcing（到预算就掐断，逼它给答案）和训练时的长度控制。
- 做 agent 架构时可以学这个分层思路，便宜层站岗，贵层只在值得的时刻叫醒。我自己的插件里，保存分诊用轻量判断，深度分析才调主模型，是同一个思想。

## 7. 给你看的思维链不等于真实推理

这是最容易被展示形式误导的一点。Anthropic 做过一系列 faithfulness 研究：给模型一个答案暗示，比如在元数据里藏「答案是 B」，模型答了 B，但思维链里经常不提这个暗示，而是编一段看起来自洽的推理。

思维链是模型生成的文本，服从语言建模目标，它不是内部计算的转录。它对「为什么是这个答案」的说明，可能是事后编出来的理由。推理模型的 CoT 比普通模型可信一些，因为 RL 训练奖励了思考和答案的一致性，但依然不能当证据用。

落地到产品里，思维链的定位应该是「有帮助的参考叙事」。展示给用户看可以，落盘供人复盘可以，拿它当「模型当时确实是这么判断的」的保证书不行。

## 8. 厂商为什么藏思维链

既然思维链有参考价值，为什么 OpenAI 和 Anthropic 要把原文藏起来。主要是两股力量在掰手腕。

一股是防蒸馏。DeepSeek-R1 开源思维链之后，很多人拿它当免费教师模型去蒸馏小模型。藏起原始 CoT、只给摘要或加密块，能抬高这个门槛。

另一股是安全审计。Anthropic 自己的研究主张 CoT monitoring 是重要的安全工具，读思维链能提前发现模型「打算」骗你的迹象。全藏起来，这个工具也没了。摘要和签名这两种折中形态，就是这两股力拉扯出来的产物。

## 9. 工程上的结论

回到我自己的流式客户端，最后的处理是这样：

- content 正常回灌，进对话历史。
- reasoning_content 走展示层和日志层，面板里给用户看，transcript 里落盘，但从不进历史。
- 代码里专门留了一行注释钉死这个约定，防止以后有人（包括我自己）觉得「这么完整扔了可惜」又把它塞回历史。

这个处理对 DeepSeek 和 Kimi 这类网关是对的。如果哪天要接 Claude 原生 API 或 OpenAI Responses API，规则就得翻过来，thinking block 和 signature 必须跟着历史走。到那时候这段逻辑要按 provider 分流，「不回灌」不是全局真理，只是当前这个协议阵营的约定。

## 10. 一个更远的变化

文本思维链本质上是把高维推理压成离散 token，信息带宽损失很大。现在有一些探索方向在尝试绕开文字，比如 Meta 的 COCONUT，在连续隐空间里推理，一步 latent thought 理论上能编码多条并行的推理路径。这类路线如果跑通，思维链的展示和回灌这套协议设计都会过时，因为到时候没有文本可以展示了。这是五年尺度的变数，现在不用为它设计什么，知道有这回事就行。
