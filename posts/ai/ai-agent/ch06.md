# RAG 检索的两种流派：BM25 与向量检索

RAG 的流水线可以简化成三步：**检索 → 组装 → 生成**。检索负责"从一堆文档里挑出跟问题最相关的几篇"，是整个系统的地基——地基歪了，后面生成再强也救不回来。

而"怎么挑"这件事，业界长期是两套并行的思路：老派的**关键词检索**（代表算法 BM25）和新派的**向量检索**（Embedding + 最近邻）。这篇把两者讲透，顺便解释为什么现代 RAG 系统普遍把两者混着用。

---

## 一、检索的本质

给定查询（query）和 N 篇文档，检索要做的是给每篇文档打一个"和 query 有多相关"的分数，然后取分数最高的 top-k。

两派的分歧只在一点：**这个"相关"用什么标准算**。

- BM25 认为：相关 = 字面词的重合程度
- 向量检索认为：相关 = 语义上的远近

---

## 二、BM25：数词的老派检索

BM25 脱胎于搜索引擎时代，核心是两个字：**数词**。

### 2.1 两个基本量

**词频（TF）**：一个词在文档里出现几次。出现越多，文档越可能相关。

**逆文档频率（IDF）**：一个词在整个语料里有多稀有。出现得越少的词，区分度越高，权重越大。比如"的""了"这种烂大街的词，权重趋近于零；"国王小道"这种罕见词，权重很高。

### 2.2 分数公式（简化版）

$$\text{score}(D, Q) = \sum_{t \in Q} \text{IDF}(t) \cdot \frac{f(t, D) \cdot (k_1 + 1)}{f(t, D) + k_1 \cdot (1 - b + b \cdot \frac{|D|}{\text{avgdl}})}$$

看着吓人，但意思就三条：

1. 查询里的每个词单独算贡献，求和
2. 词越稀有（IDF 大）、在文档里出现越多（f 大），贡献越大
3. 文档越长，每个词的贡献要被惩罚（防止长文档靠篇幅堆词频作弊）

### 2.3 特点

- **精确匹配**：只认字面。搜"攻击力"，它找不到写"伤害提升"的文档
- **快**：倒排索引 + 纯计数运算，不需要任何模型，几毫秒出结果
- **省**：CPU 就能跑，不依赖 GPU

典型实现：Elasticsearch、Lucene、rank_bm25。

## 三、向量检索：把语义变成坐标

向量检索换了个思路：**先把文本变成一串数字，再算数字之间的距离**。

### 3.1 Embedding：文本 → 向量

用一个 embedding 模型（比如 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`）把每段文本映射成高维空间里的一个点，通常 384 或 768 维：

```
"国王小道在哪"    →  [0.12, -0.45, 0.87, ...]   (384 维)
"King's Pass"    →  [0.13, -0.44, 0.86, ...]
"今天天气不错"    →  [-0.72, 0.31, 0.02, ...]
```

语义相近的文本，向量方向就接近；无关的，方向就离得远。模型在训练时见过海量文本，学到了"同义词、意译、语序变化不改变意思"这一层抽象。

### 3.2 检索：找最近的邻居

query 也过一遍模型变成向量，然后用 **FAISS**（Facebook 开源的向量索引库）在全库向量里找离它最近的 top-k。距离度量一般是余弦相似度或内积：

```python
from fastembed import TextEmbedding
import faiss
import numpy as np

model = TextEmbedding("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")

docs = ["国王小道在哪", "False Knight 怎么打", "今天天气不错"]
vecs = np.array(list(model.embed(docs))).astype("float32")

index = faiss.IndexFlatIP(384)  # 内积（配合归一化向量 ≈ 余弦）
index.add(vecs)

q = np.array(list(model.embed(["第一个 Boss 的攻略"]))).astype("float32")
scores, ids = index.search(q, k=2)
print(ids, scores)  # 命中"False Knight 怎么打"——语义匹配，不是字面匹配
```

### 3.3 特点

- **理解语义**："第一个 Boss" 能命中 "False Knight"——因为两者的向量在空间里是邻居
- **支持多语言**：跨语言模型甚至能让中文 query 命中英文文档
- **代价**：跑一次要过模型，比 BM25 重；偶尔召回"语义像但实际无关"的内容

典型实现：FAISS、Milvus、Qdrant、Chroma。

## 四、两派对比

| 维度 | BM25 | 向量检索 |
|------|------|----------|
| 匹配标准 | 字面词重合 | 语义相近 |
| 会联想同义词吗 | 不会 | 会 |
| 速度 | 极快（毫秒级） | 较快（要过模型） |
| 资源 | CPU 足够 | 需要 embedding 模型 |
| 典型失败 | "第一个 Boss" 找不到 "False Knight" | 语义像但实际无关的噪声混进来 |
| 数字敏感度 | 高（精确匹配） | 低（"回血 50"和"回血 100"向量几乎一样） |

---

## 五、各自的短板，引出"混合"

- BM25 的问题：**不会联想**。口语化、意译、跨语言的 query 直接跪
- 向量的问题：**偶尔跑偏**。召回结果里混进"语义相似但事实无关"的文档，且对精确数值不敏感

一个天然的想法：**两路都跑，结果合起来**。这就是混合检索（Hybrid Search）——见 ch07。
