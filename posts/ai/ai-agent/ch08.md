# 多阶段 RAG：从 Naive 到 Modular 的流水线

上一章讲的"混合检索 + 重排"，其实只是 RAG 流水线里的**一个阶段**。把视野拉高，整个 RAG 从"检索 → 生成"两段式，一路演进成了一条多阶段流水线。这篇按演进顺序讲清楚：Naive RAG 哪里不够，每个阶段各自补什么洞。

---

## 一、Naive RAG：基准线

最朴素的实现：

```
query → 向量检索 top-k → 拼进 prompt → LLM 生成
```

三个短板：

1. **召回不全**：query 写得不清楚时，向量检索直接跑偏；复杂问题拆不开
2. **噪声多**：top-k 里混着"语义像但无关"的内容，LLM 会被带偏
3. **幻觉没兜底**：生成完没人检查，答案可能根本不在检索内容里

多阶段 RAG 就是给这三个洞各加一道防线。

---

## 二、阶段 1：查询处理

检索之前先处理 query，让"进检索器"的问题更准。

**查询改写（Query Rewriting）**：口语化、指代不清的问题，先用 LLM 改写成适合检索的形式。

```
用户："那个回血很多的护符是啥来着？"
改写："空洞骑士中回复生命值最多的护符是什么？"
```

**HyDE（Hypothetical Document Embeddings）**：让 LLM 先写一个"假答案"，再用假答案去检索。假答案里通常包含文档里会出现的专有名词，语义命中率比裸 query 高。

**子查询分解（Query Decomposition）**：复杂问题拆成多个子查询分别检索，再汇总。比如"国王之道的护符和泪城的护符哪个更适合前期"→ 拆成"国王之道的护符"和"泪城的护符"两路。

---

## 三、阶段 2：多路召回（Recall）

这个阶段的目标是**宁可多，不可漏**——召回量取 top-50 甚至 top-100：

- BM25 路：精确词匹配
- 向量路：语义匹配
- 结构化路：SQL / 知识图谱精确查询（数值、条件筛选类问题走这里）

三路结果用 RRF 融合成一个列表（见 ch07）。

---

## 四、阶段 3：重排（Rerank）

召回阶段取的是"像"，重排阶段求的是"准"。对融合后的 top-50，用更强的模型逐篇精排，只留 top-5：

- 交叉编码器（cross-encoder）：query + doc 拼起来过模型，精度高，慢
- LLM 重排：直接让 LLM 给候选排序，最贵但最准

这一阶段是**性价比最高的一步**——不动数据、不动生成，光加一个重排器，答案质量就明显提升。

---

## 五、阶段 4：过滤与上下文组装

进 prompt 之前还有两道工序：

**元数据过滤**：按文档属性筛掉不该出现的内容。游戏助手里最典型的例子是**剧透过滤**——根据用户当前进度（已获得的能力、已击败的 Boss），把对应剧透等级以上的内容直接剔除，避免答案剧透。

**上下文压缩**：命中的文档可能很长，只保留和 query 相关的句子，而不是整篇塞进 prompt——省 token，也减少无关信息干扰。

---

## 六、阶段 5：生成与验证

生成之后再加一道**自检**，这是进阶玩法：

- **Self-RAG**：LLM 在生成时给自己的每个片段打"是否被检索内容支持"的标签，不支持就重写
- **CRAG（Corrective RAG）**：生成前先评估检索质量——检索结果太差就触发**二次检索**（换路、换 query），而不是硬着头皮生成

一句话：**把"检索错了怎么办"从人的兜底，变成系统里的一步。**

---

## 七、演进路线与落地顺序

| 形态 | 流水线 | 解决的问题 |
|------|--------|------------|
| Naive RAG | query → top-k → 生成 | 基线 |
| Advanced RAG | 改写 → 多路召回 → 融合 → 重排 → 过滤 → 生成 | 召回不全 + 噪声 |
| Modular RAG | 以上 + 验证/纠错/记忆/路由，自由组合 | 幻觉 + 复杂场景 |

落地建议按这个顺序加，每一步都是独立收益：

1. **先加重排**（改动最小，收益最大）
2. 再上混合检索（BM25 路 + RRF）
3. 查询处理（改写 / HyDE）解决"问不清楚"的问题
4. 最后才考虑 Self-RAG / CRAG 这类验证机制（成本高，且前面几步做好后收益递减）
