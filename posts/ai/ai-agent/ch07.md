# 混合检索：BM25 和向量怎么合在一起

ch06 讲了两派检索各自的问题：BM25 不会联想，向量偶尔跑偏。这章解决下一个问题：**两路都跑完之后，结果怎么合？**

这一步没有听起来那么简单——两路打分体系根本不可比。BM25 输出的是"词频加权分"，向量输出的是"余弦相似度"，数值分布完全不同，直接相加就是拿苹果加橘子。

---

## 一、混合检索的产出：两个列表

假设库里 100 篇文档，query 是"第一个 Boss 怎么打"：

- BM25 路返回：`[doc_17, doc_3, doc_88, ...]`（按 BM25 分排序）
- 向量路返回：`[doc_3, doc_42, doc_17, ...]`（按余弦相似度排序）

问题来了：doc_3 两路都排前面，doc_17 两路都在但排名不同，doc_88 只在 BM25 里出现……**最终给 LLM 的 top-k 应该是哪些？**

---

## 二、方案一：分数加权（不推荐）

$$\text{final}(d) = \alpha \cdot \text{vec\_score}(d) + \beta \cdot \text{bm25\_score}(d)$$

直觉上没问题，实际有三个坑：

1. 两路分数分布不同，必须先归一化（min-max / z-score），否则某一路天然分数大就碾压另一路
2. α、β 两个超参要调，不同数据集最优值不同，很脆
3. 归一化会被极端值带偏——一篇异常高分文档会压扁整个分布

能用，但工程上很难调稳。

---

## 三、方案二：RRF 倒数排名融合（推荐）

RRF（Reciprocal Rank Fusion）的思路很巧妙：**完全放弃分数，只看排名**。

$$\text{RRFscore}(d) = \sum_{r \in \text{rankings}(d)} \frac{1}{k + r}$$

k 是平滑常数，惯例取 60。每篇文档在**每一路**里都有一个排名 r，把 `1/(k+r)` 累加就是它的融合分。

### 3.1 为什么合理

- 不看分数 → 绕开归一化和超参的问题，两路天然可比
- 排名本身就是"相对顺序"，对极端值免疫
- 实现只要几行：

```python
def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    """rankings: 多路检索返回的文档 id 列表（已按相关性排序）"""
    scores: dict[str, float] = {}
    for ranked in rankings:
        for rank, doc_id in enumerate(ranked, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

### 3.2 效果

doc_3 在 BM25 路排第 2、向量路排第 1 → 融合分 `1/62 + 1/61 ≈ 0.0325`
doc_88 只在 BM25 路排第 3 → 融合分 `1/63 ≈ 0.0159`

两路都靠前的文档自然胜出，单路幸存者也不会完全丢失——这就是"取长补短"。

---

## 四、融合之后：重排（Rerank）

RRF 合出来的列表只能算"粗召回"——它只是把两路的排序凑在一起，并没有真正衡量"这篇文档和 query 到底有多相关"。

要提精度，再加一道**重排**：拿融合后的 top-50，用更强的模型逐篇精打细分。

### 4.1 交叉编码器（Cross-Encoder）

向量检索用的是"双塔"结构（query 和 doc 各自编码，最后算相似度），速度快但精度有上限。交叉编码器把 **query 和 doc 拼成一句话一起过模型**，模型能看到两者的完整交互，打分准得多——代价是每对都要跑一次前向，慢一个数量级。

所以标准姿势是：**粗召回用双塔/BM25 广撒网（top-50），精排用交叉编码器（取 top-5）**。

### 4.2 LLM 重排

也可以用 LLM 给候选文档打分或排序（"给下面 10 段内容按与问题的相关性排序"）。效果通常最好，但最贵，适合候选集已经很小的情况。

```python
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_community.vectorstores import FAISS

bm25 = BM25Retriever.from_texts(docs, k=50)
vector = FAISS.from_embeddings(embeddings, vectors).as_retriever(search_kwargs={"k": 50})

ensemble = EnsembleRetriever(
    retrievers=[bm25, vector],
    weights=[0.5, 0.5],        # 默认就是 RRF 融合，weights 是各路的相对权重
)
hits = ensemble.invoke("第一个 Boss 怎么打")  # 混合后的 top-k
```

## 五、双通道 vs 真融合

很多 RAG 项目（包括早期的自己）做的是"双通道"：FAISS 取 top-3、SQLite 精确查询取 top-3，两路结果**各自独立**塞进 prompt。这不算混合检索，只是把两路答案并列摆放——没有排序，LLM 得自己判断哪条更可信，经常被噪声带偏。

真正的混合检索应该是：**先融合成一个排序列表，再统一截取、统一重排、统一进 prompt**。区别就在"合"这一步，工程改动其实很小（一个 RRF 函数），收益却立竿见影。
