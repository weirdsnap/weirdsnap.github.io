# LangChain 核心概念：它到底封装了什么

裸调 OpenAI SDK 写 LLM 应用时，每个项目都会重复造这些东西：拼装 prompt 模板、解析模型输出、管理多轮消息、绑定工具。LangChain 把这些公共层抽成了统一接口。这篇讲清楚它的三层核心抽象和 LCEL 管道语法——看懂这些，就知道 LangChain 到底帮你做了什么（以及它没做什么）。

---

## 一、三层核心抽象

### 1. ChatModel：统一各家的聊天模型接口

OpenAI、Anthropic、本地模型的 API 各不相同，LangChain 用 `BaseChatModel` 统一成一个接口：进的是消息列表，出的是 `AIMessage`：

```python
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage

model = ChatOpenAI(model="gpt-4o-mini")
resp = model.invoke([
    SystemMessage("你是一个地理老师。"),
    HumanMessage("法国首都是哪？"),
])
print(resp.content)  # "巴黎是法国的首都。"
```

换厂商只改构造那一行，调用代码不变。所有 ChatModel 都实现同一套方法：`invoke`（单条）、`batch`（批量）、`stream`（流式）。

### 2. PromptTemplate：把 prompt 拼装参数化

手写 f-string 拼 prompt 很快会变成一坨字符串拼接。`ChatPromptTemplate` 把模板和参数分离：

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个{role}。"),
    ("human", "{question}"),
])
msgs = prompt.invoke({"role": "地理老师", "question": "法国首都是哪？"})
# 产出的是消息列表，可以直接喂给 model
```

### 3. OutputParser：把自由文本变成结构化数据

模型输出是文本，程序要的是字符串、JSON、列表。`StrOutputParser` 取 `.content`，`JsonOutputParser` 解析 JSON——把"解析"也变成管道里可替换的一环。

## 二、LCEL：用 `|` 把组件串成链

LangChain Expression Language（LCEL）是 0.1 之后的核心语法。所有组件都实现 `Runnable` 协议（`invoke` / `batch` / `stream`），因此可以用管道符串联：

```python
from langchain_core.output_parsers import StrOutputParser

chain = prompt | model | StrOutputParser()
result = chain.invoke({"role": "地理老师", "question": "法国首都是哪？"})
# dict → prompt 渲染成消息 → model 生成 AIMessage → parser 取出字符串
```

数据从左到右流动，每一步的输出是下一步的输入。链条本身也是 `Runnable`，可以继续嵌进更大的链。

**一个容易误解的点**：`prompt | model` 不是语法糖噱头——它让 `chain.batch([...])`、`chain.stream()` 这些方法自动对整个链条生效，不用自己写循环。批量和流式是白送的。

## 三、Tool 绑定：和 Function Calling 的对应关系

[ch02](./blog.html?post=ai/ai-agent/ch02.md) 讲过 Function Calling 的协议层。LangChain 把它封装成一行绑定：

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气。"""
    return f"{city}：晴，25°C"

model_with_tools = model.bind_tools([get_weather])
resp = model_with_tools.invoke("北京天气怎么样？")
# resp.tool_calls == [{"name": "get_weather", "args": {"city": "北京"}, ...}]
```

`@tool` 装饰器从函数签名和 docstring 自动生成 JSON Schema，`bind_tools` 把 schema 塞进每次请求的 `tools` 参数。模型的 `tool_calls` 响应解析成结构化字典——ch02 里手写的协议细节都被收进这两步。

注意 LangChain 只负责**定义和解析**，真正执行工具、把结果回注给模型的循环逻辑，是 LangGraph 做的事（见 [ch05](./blog.html?post=ai/ai-agent/ch05.md)）。

## 四、和裸调 SDK 的对比

| | 裸调 openai SDK | LangChain |
|--|----------------|-----------|
| Prompt 拼装 | f-string 手工拼 | 模板 + 参数分离 |
| 输出解析 | 自己处理 `resp.choices[0]` | parser 管道一环 |
| 换模型厂商 | 改全部调用代码 | 改构造一行 |
| 批量/流式 | 自己写 | `Runnable` 白送 |
| 工具调用 | 手写 schema + 解析 | `@tool` + `bind_tools` |
| 额外代价 | 无 | 多一层抽象，版本变动快 |

## 五、什么时候不要用它

LangChain 在社区里的争议主要两点：**过度封装**（简单脚本引入一堆概念）和**调试不透明**（链条深了以后中间步骤看不见）。经验法则：

- 一次性脚本、单次调用 → 裸 SDK 更直接
- 多步骤管道、要换模型、要批量/流式 → LangChain 开始划算
- 有状态、有分支、有循环的 Agent → 直接去 [LangGraph](./blog.html?post=ai/ai-agent/ch05.md)，不要在 LCEL 里硬拧

另外无 API key 时可以用 `langchain_core` 自带的 `GenericFakeChatModel` 在本地跑通链条逻辑，本文示例都是这么验证的：

```python
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
model = GenericFakeChatModel(messages=iter(["巴黎是法国的首都。"]))
```
