# RAG / Agent 评测体系：用数字说话，而不是体感

前面几章讲了怎么把 RAG 系统搭起来（检索、融合、多阶段流水线、复杂文档），这一章回答另一个问题：**系统改了一版，到底是变好还是变坏了？** 靠体感回答不了这个问题，评测体系的本质就是把"好不好"变成可比较的数字。

---

## 一、为什么要分层评测

RAG 系统是一条多环节的链：

```
问题 → 路由 → 检索 → 生成 → 答案
```

链条上任何一环退化，最终答案都会烂，但只看最终答案你定位不了病灶。所以评测要按环节分层，每层独立量化：

```
① 路由层   问题 → 分给了哪个知识库/工具？
② 检索层   问题 → 捞出的文档对不对？
③ 生成层   检索结果 → 答案对不对、有没有编？
④ 端到端   前三层叠加的最终用户体验
```

每层该配什么设施，取决于成本：

| 层 | 典型设施 | 成本 | 运行频率 |
|---|---|---|---|
| ① 路由 | 本地断言用例（不进 LLM） | 零 | 每次改动 |
| ② 检索 | 本地指标脚本（不进 LLM） | 零 | 每次改动 |
| ④ 端到端 | 关键词断言集 | 低 | 发版前 |
| ③④ 质量 | RAGAS（LLM 裁判） | 中 | 阶段性验收 |

核心原则：**便宜的天天跑，贵的按阶段跑**。①② 这种纯本地检查应该进 pytest，每次改动自动跑；LLM 裁判类的留给阶段验收。

## 二、检索层指标：从 Hit@k 到 Recall@k 和 MRR

很多项目的检索评测止步于 **Hit@k**：期望文档出现在 top-k 里算 1，否则算 0。这个指标的问题是粒度太粗，两种"好"分不出来：

- 期望文档排第 1 → Hit@5 = 1
- 期望文档排第 5，勉强挤进 → Hit@5 = 1

标准做法是升级成两个指标。

**Recall@k（召回率）**：

```
Recall@k = top-k 里命中的相关文档数 / 该问题的相关文档总数
```

回答"该捞的捞全了吗"。前提是你的基准题库里每条问题要标注哪些文档是相关的（可以是多个）。

**MRR（Mean Reciprocal Rank，平均倒数排名）**：期望文档排第 1 得 1 分，第 2 得 1/2，第 3 得 1/3，不在 top-k 得 0。所有问题取平均。回答"对的文档排得靠前吗"。

举个例子：两个检索器 Hit@5 都是 100%，一个把答案固定排第 1（MRR = 1.0），一个固定排第 5（MRR = 0.2）。前者明显更好，但 Hit@5 完全看不出来。这就是为什么招聘 JD 上写的是 Recall@k / MRR 而不是 Hit@k。

这两个指标**不需要 LLM**，纯离线可算。改检索参数（切分粒度、k 值、fetch_k、多路合并策略）前后各跑一次，数字对比立刻出来。在检索层优化里，这是性价比最高的一项投入。

## 三、RAGAS 四个指标

RAGAS 是 **LLM-as-judge** 的代表框架：让另一个 LLM 当裁判，按固定 rubric 给答案打分。四个指标分两对，分别对应上面分层里的检索层和生成层。

**检索质量（看 contexts）**：

- **Context Precision**：捞回来的上下文里，和答案相关的占多少、排得多靠前。我们自己的项目基线只有 0.17-0.31，意味着 top-k 里平均不到 1 条真正有用。这是检索精度的真实信号，也是重排（Rerank）阶段要主攻的数字。
- **Context Recall**：标准答案里的信息点，有多少能在 contexts 里找到依据。我们基线几乎为 0，但这个数字有方法学假象：评估时只喂了向量库 top-3，3 条片段天然覆盖不了标准答案的全部信息点。把 k 提到 5-8 再复测，才是它的真实水平。

**生成质量（看 answer）**：

- **Faithfulness（忠实度）**：把答案拆成一句句陈述，逐句问裁判"这句能被 contexts 支撑吗"，算比例，衡量"有没有编"。我们基线 0.10-0.22 看起来很吓人，但大部分是假象：系统的回答还用了结构化数据库和模型自身知识，这些不在喂给裁判的 contexts 里，全被判成"无支撑"。评测没看见系统的全部依据，不等于系统在幻觉。修法是把数据库命中也纳入 contexts。
- **Answer Accuracy**：双裁判对比答案和标准答案（两个独立 prompt 取平均，0 / 0.5 / 1 三档）。我们基线 0.58-0.75。这是终端用户视角的"答案对不对"，四个指标里最重要的一个，基线及格偏上。

读数原则：**生成类指标看绝对值（代表用户体验），检索类指标看改动前后的相对变化（指导优化方向）**。

## 四、LLM-as-judge 的可靠性坑

裁判 LLM 不是万能的，学术界已知的偏差有这么几类：

- **自偏好偏差**：裁判模型倾向于给"像自己风格"的答案打高分。如果答题和裁判用的是同一家模型，这个偏差理论上就存在；缓解办法是裁判换一家模型，或者至少在读数时意识到它。
- **位置偏差 / 冗长偏好**：更长、更自信的答案容易得高分。
- **rubric 敏感性**：prompt 措辞变了分数就会漂。所以**指标只能纵向对比同一版本的裁判**，不能拿 RAGAS 0.1 的报告和 0.4 的比。

基于最后一点，报告里必须标注评测组合：哪个裁判模型 + 哪个 RAGAS 版本。换裁判或升版本，旧基线作废重测。ARES 框架的思路（微调专用裁判 + 统计置信区间）就是针对这类可靠性问题的，值得单独关注。

## 五、Golden Set：评测的地基

所有指标都建立在一份标注的基准题库上。它要满足四个条件：

1. **有标准答案（ground truth）**：Answer Accuracy 和 Context Recall 都拿它当参照。
2. **覆盖有代表性的问法分布**：不是随机凑题，要按真实用户问法分层。拿游戏问答场景举例：位置查询、数值属性、Boss 打法、配方合成、带剧透前提的问题、边界问题（知识库没有的、跨库的）。
3. **进 git、可复现**：它是测试代码，不是一次性脚本。
4. **规模 30-50 条起步**：少于 30 条统计噪声太大，一道题失败就是 3 个点的波动。

落地时不用从零出题：项目里散落的测试用例往往可以直接转化。检索层的断言用例（有期望文档）天然就是 Recall@k 格式；端到端的关键词断言集补上标准答案就能进 golden set；已有的 RAGAS 评估题扩充覆盖面即可。合并去重、统一格式、标注题型，就得到了第一版地基。

## 六、评测驱动的开发节奏

整套体系搭好后，日常工作流变成一个循环：

```
改检索 / 提示词 / 路由 → 跑 pytest（秒级，防回归）
                      → golden set 检索指标（分钟级，看 Recall@k / MRR 变化）
                      → 重大改动跑 RAGAS（小时级，看 Answer Accuracy 变化）
                      → 报告落盘，和上版基线 diff
```

**"改动前后能 diff"比单次绝对值重要得多**：单次 0.65 说明不了什么，但从 0.60 → 0.65 且知道是哪个改动带来的，就是工程价值。所以评测报告要带时间戳落盘，保留趋势对比的能力。
