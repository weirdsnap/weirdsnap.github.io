# 读指标的几个坑：分位数、load average、内存口径、PV/UV

这半年给 GameGuide 搭了个看板，把每轮问答的耗时、token、失败率、博客访问都堆到一页上。写统计层的时候踩了不少「数字看着对、结论是错的」的坑，回头整理一下这些通用指标到底在数什么。

---

## 均值骗人，用分位数

同一批耗时数据，报均值能得出「服务挺快」，报 p90 能得出「用户每十次就撞一次 30 秒」。两个数都没造假，是分布决定的：耗时、token 这类指标天生长尾，少数慢样本能把均值拉离典型值。

一组真实数据（7 天，137 轮问答）：

| 口径 | 值 |
| --- | --- |
| 均值 | 17.4s |
| p50 | 15.4s |
| p90 | 29.6s |
| p99 | 47.2s |
| max | 65.4s |

p50 和均值差 2 秒不算多，但 p90 是 p50 的两倍，说明有相当一部分请求撞上了工具调用次数多、上下文长的路径。预算线只能拿 p90 定，拿均值定等于默许一半以上请求超线。

分位数怎么算也有讲究。插值算法（线性插值、取中值）和最近秩算法在小样本上结果不一样。我用的是最近秩，排序后取 `idx = round(p * (n - 1))`，不插值，好处是结果一定落在真实样本上，坏处也明显：

**n 小的时候 p90 没有意义。** n = 4 时 `round(0.9 * 3) = 3`，p90 就是最大值本人。所以样本少于三十来个的时候，p90 上蹿下跳不代表回归，先看样本量再看阈值。我给 turns_report 加了 `--check-budget`，但那个东西只在窗口够大时才值得信。

## load average 数的是任务，不是百分比

`/proc/loadavg` 三个数，1、5、15 分钟。它不是 CPU 使用率，是「平均有多少个任务在等 CPU 或者在不可中断睡眠里」。内核用指数衰减平均算出来的，所以它对突发的反应很慢，对持续负载的刻画很准。

三个容易翻车的地方：

- **跟核数比才有意义。** 2 核机器 load 1 是半载，load 2 才是满载，load 4 已经开始排队。单看 load 数值没有对错。
- **D 状态也算进去。** 卡在磁盘 IO 或网络文件系统的进程进 D 状态，不动 CPU 也抬 load。所以 load 高而 CPU 低，八成是 IO 卡住，不是算力不够。
- **容器里读到的 load 是宿主机的。** `/proc/loadavg` 不做 cgroup 隔离，容器里看到的是整台物理机的数字，拿它评估自己配额会得出很离谱的结论。

我自己的机器还有个反向坑：2 核 3.7G 的小 VM，CPU 常年 20% 以下，load 常年在 0.2 上下。CPU 压根不是瓶颈，真瓶颈是内存和 swap。这种场景盯着 load 看会以为一切健康。

## 内存的四个口径，别混着看

`free` 的默认输出里有 free、buffers、cache、available，很多人只看第一列然后以为内存要炸。

- **MemFree**：完全没被用的物理页。低是正常的，内核把空闲内存拿去做 page cache 了，文件读得快就靠它。
- **MemAvailable**：内核估的「能腾给新进程用多少」，包含可回收的 page cache。这才是判断内存压力的指标。
- **swap 当前用量**：被换出到磁盘、现在还在 swap 里的量。跟 **swap 累计换出页数**（`vmstat` 的 `so`、`/proc/vmstat` 的 `pswpout`）完全是两码事，后者是累计计数器，只增不减，看到 183 万页别慌，那是这台机器从开机到现在的历史总量。
- **RSS 与 VSZ**：VSZ 包含 mmap 了但没摸过的页，虚得没边；RSS 是真正驻留的物理页。但 RSS 会把共享库和共享内存重复计到每个进程头上，多进程场景想算准得看 PSS。

顺带一个实践结论：swap 用量的阈值别按比例拍，按这台机器的历史表现定。我的 VM swap 长期在 1.6G 以上（总共 2G），那不是异常状态，是常态。突然跳上去才是信号。

## PV 和 UV：口径不同，比值的意义也不同

静态博客没有后端，文章级访问只能靠前端 beacon 上报，所以这两个数都是我自己定义的：

- **PV**：窗口内有效上报条数。刷新一次算一次，预渲染/预取也会上报，爬虫如果 UA 不像爬虫也会混进来。所以 PV 天然偏高。
- **UV**：上报里的访客标识去重后的数量。标识怎么生成直接决定口径。用 cookie 会被清、用指纹会跨设备串号，我用的是「每天换盐的 HMAC(IP + UA)」：同一天同一个人算一个，跨天认不出来。

这个实现带来的后果要显式接受：**同一个人连来三天，算 3 个 UV。** 好处是不需要 cookie 横幅、跨天无法串联同一个人，坏处是 UV 只能是「人次」而不是「人数」。要报「独立访客」就得换方案，要隐私就留下这个偏差，二选一。

UV/PV 的比值也不是「读完率」。它只说明平均每人上报了几次，页面内滚动、点击都不上报的话，比值低更可能是在刷新。想让它有解释力，得先保证两类事件口径一致。

## 成功率不等于满意度

失败率好算：`error` 字段非空或者路由直接落 error 的轮次，除以总数。但它只覆盖「异常退出」这一类。

答非所问、检索没命中、模型说查不到，全都是 HTTP 200 加一段正常回答，失败率里一个都不算。我线上跑了一周，失败率 0%，用户却在连续几天高强度使用同一个功能，说明真正的质量问题不在报错上。

这种就得靠第二个信号。我做了点赞点踩，落库时带 `turn_id`，统计时按 `turn_id` 去重取最后一次（同一轮改主意只算最后一票），再算差评率。更靠谱的是人工抽检，但那玩意儿没法自动化。

经验是：**成功率告诉你系统还活着，满意度才告诉你它有没有用。** 两个都要，缺一个就会得出「指标很好、产品很烂」或者反过来的结论。

## 采样、下采样与窗口

三个跟「时间」有关的坑，都是看完数之后才发现读错的：

- **采样间隔决定能看见什么。** 系统资源 30 秒采一次，写进 JSONL 保留 7 天。30 秒以内的尖峰根本采不到，这不是 bug，是在拿精度换存储。
- **画图会二次失真。** 7 天的数据有近 3000 个点，压成 180 个桶画折线，我原来用每桶取均值，图表很好看，尖峰全被抹平了。要看尖峰就得改成取桶内最大值或者 p95，代价是曲线毛躁。取什么统计量要跟用途对齐。
- **窗口会混进不同版本的样本。** 我把上下文裁剪上线后看 7 天窗口的 p90，数字比上线前还高，差点当成回归去查。真相是窗口里混着上线前的旧进程轮次。要么按部署时刻切分（`--since "2026-11-27 19:45"`），要么老老实实只看上线后的样本。

顺带一个分页的坑：轮次明细按时间排序分页，同一秒可能落好几轮，只用时间戳做游标会漏行或者重复。复合游标 `(ts, id)` 才稳，两个参数必须成对传。

## 一张对照表

| 指标 | 常见误读 | 正确读法 |
| --- | --- | --- |
| 均值 | 「平均这么快，没问题」 | 长尾分布下均值不代表典型值 |
| p90 | 「今天 p90 很高」 | 先看样本量，n < 30 时 p90 就是最大值 |
| load average | 「load 2 就是 100%」 | 除以核数才是利用率；D 状态也计入 |
| MemFree | 「内存快满了」 | 看 MemAvailable |
| swap 累计换出 | 「swap 炸了」 | 只增计数器，看当前用量 |
| RSS | 「进程占这么多内存」 | 共享页重复计，多进程看 PSS |
| PV | 「多少人看过」 | 刷新和爬虫都算，是次数 |
| UV | 「多少独立访客」 | 看去重方案，按天换盐就是人次 |
| 失败率 | 「服务很健康」 | 只覆盖异常退出，答非所问不算 |
| 7 天 p90 | 「回归了」 | 窗口可能混着旧版本样本 |
