# 代理为什么比直连慢：用户态转发与两段 TCP

家里手机刷小红书，视频一直转圈。我一开始怀疑分流规则写错了，抓了日志发现匹配的是 `GeoIP(cn) using DIRECT`，也就是流量老老实实走直连。问题不在规则上。顺着这个线索下去，才把「代理到底慢在哪」这件事想清楚。

---

## 直连的数据路径

手机访问 bilibili 的 CDN，包从无线口进路由器，经过上一篇讲的那套：桥转发、IP 层、conntrack、NAT，然后从 pppoe-wan 出去。整条路径在内核里完成，没有任何用户态进程参与。

即使没有任何硬件加速，这条路也是单次转发。CPU 做的活是查路由、查 conntrack、改包头、把 skb 交给网卡驱动，全是内核函数调用，不用切进程。

---

## 走代理时多了什么

手机把 Wi-Fi 代理设成 `192.168.5.1:7890`，情况就变了。以 HTTP 代理访问一个 https 站点为例：

1. 手机和路由器的 7890 端口建立一条 TCP 连接（第一段）
2. 手机发 `CONNECT www.example.com:443`，代理进程读这个请求
3. 代理进程自己对外发起一条 TCP 连接（第二段），完成 TLS 握手
4. 之后手机上行的数据：手机 → 第一段 TCP → 代理进程 read → 代理进程 write → 第二段 TCP → 公网
5. 下行反过来再做一遍

第 4 步就是关键。数据在代理进程里被**完整地搬了两次**：一次从内核 socket 缓冲区 read 到用户态内存，一次从用户态 write 回内核。每一次 read/write 都是一次系统调用，都涉及一次用户态和内核态的切换。一个视频流的每个 TCP 包都要走这么一遍。

于是同一条流量经过的环节从「内核转发一次」变成了「内核收发两次 + 用户态搬两遍」。

---

## 开销到底有多大

用 `iperf3` 这种纯吞吐测试，一个用户态代理跑满百兆并不难，跑满千兆就吃力了。原因是拷贝和上下文切换都是纯 CPU 活，还只用一个核心（单个 TCP 连接的收发通常在同一个线程里，即使多核也帮不上忙）。

更要紧的是并发的时候。视频网站一个片子拆成几百个分片，每条都是独立连接，每一条都要单独走一遍上面的流程。这时候 CPU 要同时处理几百组 read/write，还要做 TLS、加解密、规则匹配。这台 AX3600 是四核 A53，跑着 mihomo、Caddy、一个游戏服务器，本来就没什么余量。

---

## 一个容易误判的地方：延迟不是瓶颈

第一次 curl 一个远端地址花了 14.7 秒，第二次 1.8 秒。看起来像是代理不稳定，其实是新出口的 TLS 冷启动：DNS 要解析、TCP 要握手、TLS 要协商，第一次还要等远端节点的连接池建立起来。第二次复用了这些状态，就快了。

这类「首次慢、之后正常」基本都不是带宽问题，而是握手和建连的成本。反过来，视频一直缓冲、进度条卡住不动，才是吞吐不够的典型表现。区分这两者很重要，否则会往错误的方向调优。

---

## 为什么绕不过去

有人会想：代理进程能不能不经过用户态？答案是不能，除非用内核态的转发方案。

代理要做的事本质上需要判断：这条流量属于哪个域名、该走哪个出口、要不要改目标。这些信息在内核的 conntrack 里是没有的（conntrack 只记五元组）。所以必须有一个用户态程序解析请求、做决策，再把数据重新送出去。

这也是为什么 TUN 方案的性能瓶颈同样存在：包从内核网络栈转进 tun 设备，用户态程序读走，处理完再写回内核。只是它省掉了「两段 TCP」，换成了「一次 IP 层进出」，对于 UDP 和大流量多少好一些。

---

## 我们最后怎么处理的

既然代理本身有额外成本，那就让不该走代理的流量别走代理。

手机 Wi-Fi 设置里可以填一个 PAC 地址，浏览器和 App 拿到的是一段 JS，由它决定某个 URL 是直接连还是走代理。视频、图片、购物这类国内大带宽流量全部 `DIRECT`，只把确实要经代理的域名交给代理。

这条路不是没有代价的：PAC 只能看到 URL，看不到 IP 和端口，纯 IP 的连接管不了；域名清单也要自己维护。但它把「两段 TCP + 用户态搬运」从视频这类最吃带宽的场景里彻底拿掉了，代价小得多。

---

## 小结

- 代理的慢来自两段 TCP 加两次用户态拷贝，不是规则问题。
- 吞吐瓶颈在 CPU 和单连接串行处理上，多核帮不上单条连接的忙。
- 首次慢属于握手成本，和带宽不足是两回事，别混着调。
- 真正有效的优化不是让代理更快，而是让不该走代理的流量别走代理。
