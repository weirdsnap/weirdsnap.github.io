# 透明代理的三种做法：REDIRECT、TPROXY 与 TUN

「透明代理」指的是客户端不用配置任何东西，流量自动被接管。听起来比手动填 7890 省事，实现起来有三条完全不同的路，踩的坑也各不相同。这篇把三种做法的原理和适用边界理一遍。

---

## 为什么需要「透明」

手动配代理有个硬伤：有些设备配不了，比如电视盒子、某些 IoT 设备；有些程序根本不读系统代理设置。想强制接管，就得在路由器这一层动手，让流量在离开设备之前被改道。

改道的地方只有两个：`PREROUTING`（包刚进路由器，还没做路由决策）和 `OUTPUT`（路由器自己发出的包）。

---

## 做法一：REDIRECT

nat 表里的一条规则：

```sh
iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-ports 7890
```

`REDIRECT` 做的事是把目标地址改成路由器自己（127.0.0.1），端口改成 7890。代理进程收到连接后，靠 `SO_ORIGINAL_DST` 这个 socket 选项把「原来的目标地址」取回来，才知道用户其实要访问哪里。

它的限制很明显：

- 只能写 `-p tcp`，UDP 支持不了（QUIC、DNS over UDP 都漏）
- 目标地址被改掉了，代理必须取原始目标，实现上依赖 `SO_ORIGINAL_DST`
- 走的是 nat 表，只在新建连接的第一个包上生效

REDIRECT 是最老最省事的方案，很多教程里都是它。只处理 HTTP/HTTPS 够用了。

---

## 做法二：TPROXY

`TPROXY` 在 mangle 表的 `PREROUTING` 里工作，特点是**不改目标地址**，只是给包打一个标记（mark），让内核把它交给本地的一个 socket。

代价是需要配合策略路由：

```sh
ip rule add fwmark 1 lookup 100
ip route add local 0.0.0.0/0 dev lo table 100
```

含义是：带 mark 1 的包去查 100 号路由表，那张表里所有目的地都是 `local`，也就是交给本机。这样包的目标地址虽然还是公网 IP，但内核认为它是发给自己的，于是送进本地 socket。代理进程用 `IP_TRANSPARENT` 选项绑定，就能拿到完整的原始目标。

比 REDIRECT 强的地方：

- 支持 UDP（`--on-ip` 加 `-p udp`）
- 目标地址没丢，不需要 `SO_ORIGINAL_DST`

麻烦的地方在内核配置：需要 `xt_TPROXY` 模块（内核选项 `CONFIG_NETFILTER_XT_TARGET_TPROXY`），还要配策略路由和 mark。OpenWrt 上对应的是 `kmod-ipt-tproxy` 和 `iptables-mod-tproxy` 两个包，缺一个都加载不了规则。

---

## 做法三：TUN

TUN 是一个虚拟网络设备。创建 `/dev/net/tun` 的实例之后，内核会把它当成一块网卡，往这块「网卡」发的包不会真的出去，而是被用户态程序读走。

配置顺序是：

1. 创建 tun0
2. 在路由表里把要代理的网段指到 tun0
3. 用户态程序从 tun0 读 IP 包，自己决定怎么处理，处理完再写回 tun0 或直接发出去

TUN 的优点是不需要 iptables 规则，也不需要改客户端任何设置，整条 IP 层都能接管，UDP 天然支持。它也是 Clash、sing-box 这些工具在手机上做 VPN 模式的原理。

缺点是它和 DNS 绑得很死。因为拿到的是 IP 包，程序需要知道这个 IP 对应哪个域名才能做规则匹配，于是发明了 fake-ip 这套东西，下一节细讲。

TUN 还有一个不明显的坑：如果代理只在一台机器上跑（比如路由器），把默认路由指到 tun0 就是把整台机器的流量都劫持了，包括代理程序自己连接上游节点的流量。必须留一条例外路由，否则直接成环。

---

## 三种方案的对照

| | REDIRECT | TPROXY | TUN |
|---|---|---|---|
| 工作层 | nat / PREROUTING | mangle / PREROUTING | 虚拟网卡 |
| 是否改目标地址 | 改 | 不改 | 不涉及 |
| UDP | 不支持 | 支持 | 支持 |
| 需要策略路由 | 否 | 是 | 是 |
| 需要额外内核模块 | 否 | xt_TPROXY | tun |
| 客户端要配什么 | 无 | 无 | 无（需 DNS 配合） |

---

## 我们为什么没走这条路

我们的场景很朴素：家里几台手机、一台电脑，要的只是「能配代理的设备配一下，不能配的算了」。直接让手机填 `192.168.5.1:7890`，配合 PAC 分流，已经解决实际问题。

透明代理省的是「每台设备填一次」这一下，代价是要动内核模块、策略路由、DNS。这台路由器本来就在为内存和内核模块发愁（下一篇会讲 NSS 的坑），不想再往这套东西上加依赖。

判断标准其实很简单：设备数量少、都能手动配，就别上透明代理。设备多、有盒子和电视这种配不了代理的东西，再考虑 TPROXY 或 TUN。

---

## 小结

- REDIRECT 最省事，只支持 TCP，靠 `SO_ORIGINAL_DST` 取原目标。
- TPROXY 保留原始目标地址，支持 UDP，但需要 xt_TPROXY 和策略路由。
- TUN 接管整个 IP 层，天然支持 UDP，代价是必须处理 DNS 与路由环路。
- 要不要上透明代理，看设备能不能手动配，而不是看哪个方案更酷。
