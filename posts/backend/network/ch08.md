# PAC：把代理决策交给客户端

前几篇反复提到 PAC 分流，这篇单独讲它。PAC 是 Proxy Auto-Config 的缩写，本质是一段 JS：客户端访问某个 URL 之前，先调用这段脚本里的函数，由它告诉客户端「这个网站直连」还是「走代理」。

它解决的是代理架构里最不划算的一环：让路由器替所有流量做决定。

---

## 函数签名很简单

PAC 文件必须提供一个全局函数：

```js
function FindProxyForURL(url, host) {
  if (shExpMatch(host, "*.xiaohongshu.com")) {
    return "DIRECT";
  }
  return "PROXY 192.168.5.1:7890";
}
```

返回值有三种基本形式：

- `DIRECT`：直接连
- `PROXY host:port`：走 HTTP 代理
- `SOCKS host:port`：走 SOCKS 代理

也可以用分号写多个，前面的失败了试后面的，比如 `PROXY 192.168.5.1:7890; DIRECT`。

`url` 是完整地址，`host` 是其中的主机名。HTTPS 的路径也是可见的（浏览器把完整 URL 传进来），但请求内容看不到，所以按域名匹配是主要手段。

---

## 为什么它能提速

关键在于**决策位置变了**。

路由器侧分流的时候，所有流量都已经先进入路由器，再判断走哪条路。哪怕结论是直连，包也已经走过了「代理进程 —— 直连出口」这段额外的用户态路径。这就是上一篇讲的成本。

PAC 把判断提前到了客户端。客户端一旦拿到 `DIRECT`，流量就按它原本的路径直连，路由器只做普通的转发和 NAT，一步都不多走。只有返回 `PROXY` 的流量，才额外付出用户态中继的代价。

于是国内那些最吃带宽的东西都不再碰代理：视频、图片、直播、购物 App 的 CDN 全是直连，只剩下本来就必须走代理的域名在付成本。

---

## 部署方式

把 PAC 文件放到路由器的 Web 目录（OpenWrt 上是 `/www`），手机 Wi-Fi 设置里选「代理：自动配置」，填 `http://192.168.5.1/proxy.pac` 就行。电脑同理，系统网络设置里填这个 URL。

写这个文件有两个实操坑：

一是别在终端里逐段粘贴。多行 JS 粘贴进终端会被吃掉星号、长行被折断，结果就是字符串跨行，语法错误但报错信息莫名其妙。正确做法是在本地把文件写好，用 SFTP 传上去，或者 `cat > /www/proxy.pac` 之后粘贴一次再 `Ctrl-D`，但也要检查有没有展开的变量。

二是改完要清缓存。浏览器和系统都会缓存 PAC，改了几分钟没生效，先怀疑缓存。手机最省事的办法是关掉再打开 Wi-Fi。

---

## 脚本里的限制

PAC 运行在一个沙箱里，能用的函数只有一批历史遗留的辅助函数：`dnsDomainIs`、`shExpMatch`、`isPlainHostName`、`dnsResolve` 等。没有 `fetch`、没有 `setTimeout`、没有 `console`。`dnsResolve` 虽然能用，但每次调用都可能是一次同步 DNS 查询，大量使用会拖慢每个请求。

所以脚本写法很土，基本就是一堆 `if` 加字符串匹配：

```js
function FindProxyForURL(url, host) {
  if (isPlainHostName(host)) return "DIRECT";
  if (shExpMatch(host, "*.xhscdn.com")) return "DIRECT";
  if (shExpMatch(host, "*.bilivideo.com")) return "DIRECT";
  if (dnsDomainIs(host, ".taobao.com")) return "DIRECT";
  return "PROXY 192.168.5.1:7890";
}
```

`shExpMatch` 支持 shell 通配符，`dnsDomainIs` 做后缀判断。注意 `dnsDomainIs(host, ".taobao.com")` 这个写法带前导点，语义是「以 .taobao.com 结尾」，比 `shExpMatch` 更不容易误伤。

---

## 它管不了什么

PAC 的能力边界很清楚：

- 只处理 HTTP、HTTPS、FTP 这类有 URL 的协议。游戏、SSH、自定义端口的 TCP 都管不了，这些流量该直连就直连（不受影响，因为没配全局代理）。
- 只能看到域名和路径，看不到端口和协议内部的差异。
- 返回值只有 DIRECT 和代理两种，没有「按域名走不同出口」这种能力。多节点择优要靠代理软件自己的策略组。
- 客户端不读 PAC 的程序依旧需要手动配代理，或者根本连不上。

我们的用法是白名单式：PAC 里列出四十多个国内大带宽域名，其余一律走代理。这样最常用的视频、图片、购物全部直连，剩下的站点本来量也不大，走代理的成本可以接受。

漏网在所难免：新出现的国内 CDN 域名没写进去，就会走代理，可能变慢；某个需要代理的站点如果被误写进 DIRECT，就打不开。两种情况的处理都一样，看到现象、加一条、清缓存，完事。

---

## 小结

- PAC 是一段 JS，由客户端的 `FindProxyForURL` 决定每个 URL 走不走代理。
- 决策放在客户端，直连流量不再经过路由器的代理进程，这是它提速的原理。
- 沙箱里只有几个字符串辅助函数，脚本写法朴素，靠域名匹配。
- 只管得住有 URL 的协议，管不了的流量靠「不配全局代理」来保证直连。
- 维护成本是手动清单，配合白名单思路可以接受。
