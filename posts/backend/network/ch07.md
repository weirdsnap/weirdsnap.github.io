# 硬件转发为什么没跑起来：NSS、ECM 和一块缺失的模块

前几篇一直说「路由器所有流量都是纯 CPU 软件转发」。这个结论不是查文档查来的，是折腾了一下午硬件加速之后确认的。这篇把过程和数据留个记录，也顺便讲清楚 Linux 上「转发加速」到底有几层。

---

## 起因

视频卡的时候，第一反应是代理太重。但直连的国内流量也谈不上快，就想到一个可能：这台路由器宣传里写了硬件转发，是不是根本没启用？

型号是小米 AX3600，芯片高通 IPQ8071A。这颗芯片除了四个 CPU 核，还有一套独立的网络子系统（NSS），专门做转发、加解密、QoS 这些重复性的网络工作。理论上包进了 NSS 就不占用 CPU，千兆线速转发、小包处理都不会成为瓶颈。

问题在于，用不用得上要看固件有没有把这一整套东西接好。

---

## 先分清两层加速

Linux 上的转发加速有两个完全不同的层次，很容易混。

第一层是**软件快速路径**，也就是 flowtable。内核在 netfilter 里加了 `FLOWOFFLOAD` 机制：一条连接的前几个包还是老老实实走规则遍历，之后内核把它记进 flowtable，后续的包直接绕过整条 netfilter 链，只做必要处理。它省的是「每条规则都要匹配一遍」的开销，跑的仍然是 CPU。

第二层是**硬件卸载**，把整条流直接交给芯片里的转发引擎，CPU 完全不参与。NSS 属于这一层。

两层是独立开关，可以都开，也可以都不开。我们这台，两层都没生效。

---

## flowtable 那层：直接不可用

OpenWrt 的防火墙配置里有：

```
option flow_offloading '1'
option flow_offloading_hw '1'
```

改成 1 之后重启防火墙，日志里出现：

```
fw3: ... requires unavailable target extension FLOWOFFLOAD, disabling
```

fw3 需要内核里的 `xt_FLOWOFFLOAD` 模块来下发规则，这个固件没编进去。于是设成 1 也会被自动禁用，配置看着是开的，实际是关的。`flow_offloading_hw` 更不用说，依赖 NSS。

---

## NSS 那层：零件齐了，但没接线

先看零件在不在。`lsmod` 里能看到 `qca_nss_drv`、`qca_nss_dp`、`qca_nss_bridge_mgr`、`qca_nss_pppoe`、`qca_ssdk`、`ecm`，固件包 `nss-firmware-ipq8074` 也装着，`/sys/kernel/debug/ecm/` 下的目录结构完整，`ecm_db`、`ecm_nss_ipv4`、classifier 全都有。

看起来全套都在。但判断加速有没有真的生效，不能看目录，要看计数：

```sh
cat /sys/kernel/debug/ecm/ecm_db/connection_count_simple
```

输出是这样的：

```
tcp 51 udp 95 other 0 total 146
```

`simple` 是「没被硬件接管」的连接数。这里 total 正好等于 tcp+udp+other 之和，意味着每一条连接都在 simple 里，一条都没走硬件路径。如果加速生效，应该有连接脱离 simple，total 大于三项之和。

另一个判据是 `/sys/kernel/debug/ppe/` 这个目录。PPE 是包处理引擎，加速生效时这里会有表项。我们这台没有这个目录。先确认过 debugfs 已经挂载，排除了「没挂载所以看不到」的可能。

---

## 找根因：异常计数指向哪个环节

`ecm` 提供了异常统计：

```sh
cat /sys/kernel/debug/ecm/stats/ecm_v4_exception_stats
```

一堆计数里，绝大多数是 0：`v4_front_end_stopped` 是 0（前端没停），`*_accel_not_supported` 是 0（硬件没拒绝）。只有一项在持续增长：

```
v4_bridge_routed_packet_wrong_hook : 103502
```

`wrong_hook` 的意思是：这个包挂在了错误的 netfilter 钩子上，ECM 认不出它该不该被加速。

与此同时，防火墙启动脚本在报错：

```
/etc/firewall.d/qca-nss-ecm: iptables: Couldn't load match 'physdev'
```

`physdev` 是 iptables 的一个匹配扩展，作用是判断包从哪个桥接端口进来、要往哪个桥接端口出去。原因是路由器有多个 LAN 口和无线口，全都挂在 `br-lan` 这一个软件桥上。ECM 要给连接分类，必须知道这个包实际走的是哪个物理端口，否则没法把它挂到正确的钩子上。

这正是 `wrong_hook` 的来源：不知道包从哪进来的，钩子就挂错了，硬件永远接不住。

---

## 为什么补不上

`Couldn't load match 'physdev'` 说明缺的是 iptables 扩展。这里有个值得记住的知识点：iptables 的每一个 match 和 target，都由两半组成。

- 内核态：`xt_physdev.ko`，在 `/lib/modules/$(uname -r)/` 下，负责真正的包处理逻辑
- 用户态：`libxt_physdev.so`，在 `/usr/lib/iptables/` 下，负责把命令行参数翻译成内核能懂的结构

两半缺任何一半，规则都加载不了。我们这台是两半都缺：内核模块目录里没有 `xt_physdev.ko`，用户态库目录里也没有 `.so`。

试着用 opkg 装。官方源给的是 OpenWrt 24.10.1，内核 6.6；这台固件是恩山自编的，内核 6.12.30。内核模块必须和内核版本严格对齐，装上去也加载不了。补这个模块只能等固件更新，或者自己编译。

试过最后一招：把 `enable_bridge_filtering` 关掉，看能不能绕开桥相关的分类逻辑，让硬件至少接管一部分直连流量。命令都是成功的，重启 ECM 之后计数清零，再刷一会儿流量，`wrong_hook` 又从 0 涨到十万级。无效。

---

## 结论

这台路由器上的硬件加速从来没有生效过，所有转发都是纯 CPU 软件路径，也没有 flowtable 快速路径可以兜底。

这件事修正了我之前的一个判断错误。之前我以为「开代理绕开了硬件 NAT offload」，实际情况是根本没有 offload 可绕。代理相对于直连多出来的开销，全部来自前面讲的两段 TCP 和用户态中转，跟硬件加速无关。

500M 宽带的量级，四个 A53 核做软件转发是够的，视频的问题最后是用 PAC 分流解决的，不是靠基础设施提速。

想真正用上 NSS，得换一个把 physdev 和整套 NSS 依赖都打包完整的固件。为这个换固件、承担变砖风险，收益不匹配。

---

## 小结

- 转发加速分两层：内核 flowtable（省规则遍历）和硬件卸载（CPU 完全不参与）。
- 判断硬件是否生效，看 `ecm_db/connection_count_simple` 的 total 是否大于三项之和，别只看目录。
- `wrong_hook` 增长说明包挂在错误的钩子上，分类环节缺信息。
- iptables 的 match 有两半：`xt_*.ko` 和 `libxt_*.so`，缺一个都加载不了。
- 自编内核的固件补不了官方源的模块，版本必须严格匹配。
