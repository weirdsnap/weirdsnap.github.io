# GEOSITE 和 GEOIP 匹配的到底是什么

分流规则里最省事的两类规则是 `GEOIP,CN,DIRECT` 和 `GEOSITE,gfw,PROXY`。它们背后是两份数据库文件，一个按 IP 网段分类，一个按域名分类。搞清楚这两份东西的格式和来源，就不会再被「为什么我写的 openai 规则没生效」这类问题绕住。

---

## GEOIP：按 IP 归属分类

`GEOIP` 规则判断的是目标 IP 属于哪个国家或地区。它读的数据库通常是一个 `.mmdb` 文件（MaxMind 格式），里面是「CIDR 段 → 国家代码」的映射表，几万条。

```yaml
  - GEOIP,CN,DIRECT
```

这条规则的意思是：如果目标 IP 落在数据库标注为 CN 的网段里，走直连。

运行时它需要知道目标 IP，所以对域名连接会先触发一次解析。这也是前面提到 `no-resolve` 的原因。

能查的只有「国家」这一维度，因为 mmdb 里就只有这一层。这解释了一个常见困惑：网上有教程写 `GEOIP,openai,PROXY`，复制到自己的配置里却不生效，因为 openai 不是一个国家，mmdb 里没有这个分类。

---

## 要让 GEOIP 支持自定义分类，得换数据库格式

除了 mmdb，还有另一种格式叫 GeoIP.dat，是 V2Ray 那套 geodata 规范。它允许「自定义分类」：除了 `cn`、`private` 这种国家分类，还能有 `telegram`、`google`、`openai`、`netflix` 这类按服务划分的集合。

切换到这种格式要做两件事：

1. 确认 geodata 模式开启（mihomo 里是 `geodata-mode: true`）
2. 让 GeoIP.dat 和 GeoSite.dat 放在数据目录里

只改规则、不改数据库格式，`GEOIP,openai` 依然匹配不到任何东西，也不会报错，只是永远不命中。这类静默失效最难查。

---

## GEOSITE：按域名分类

`GEOSITE` 判断的是域名属于哪个集合。它读 GeoSite.dat，里面是按站点组织的域名列表，分类名和 GeoIP 的类似：

```yaml
  - GEOSITE,gfw,PROXY
  - GEOSITE,youtube,PROXY
  - GEOSITE,cn,DIRECT
```

`gfw` 这一类是社区维护的「被墙站点」清单，包含常见被屏蔽的域名。它比手写几百条 `DOMAIN-SUFFIX` 省事得多，也是我们最后采用的方案：一条 `GEOSITE,gfw,PROXY` 顶掉一张自己维护的清单。

域名集合的好处是不用解析 IP，规则匹配在收到域名的时候就能完成，没有额外的 DNS 开销。代价是它只管域名，纯 IP 的连接命中不了。

---

## 代价：启动时间和内存

geodata 是全量加载进内存的。规则总数六千多条的时候，启动要多等九秒左右。

这台路由器的内存总共 414MB，跑着 mihomo、Caddy、游戏服务器，本来就不宽裕。加载 GeoSite.dat 的时候会有一个明显的内存峰值。踩过的坑是：在已经有一个 mihomo 实例运行的情况下再跑一次配置检查（`clash -t`），两份数据同时加载，直接 OOM，进程被内核杀掉，日志停在加载规则那一行。

所以在这台机器上改配置的流程是：改完直接重启，用真实流量验证，不做预检查。回滚靠两条 sed，比跑一次 `-t` 安全。

---

## 分类内容会滞后

无论是 GeoIP 还是 GeoSite，数据都是定期从上游仓库拉取的。新出现的站点、换过的 IP 段，都要等数据更新之后才能匹配到。所以「昨天还能用今天不行了」这种情况，第一反应应该是看规则命中情况，而不是马上怀疑配置写错。

我们的处理方式是留一手：`GEOSITE,gfw` 之后还有兜底的 `MATCH,DIRECT`，漏网的站点打不开时手动补一条 `DOMAIN-SUFFIX` 放到最前面。白名单式维护，接受偶尔需要手动补。

---

## 小结

- GEOIP 按 IP 归属国家分类，只读 mmdb 时只有国家这一维。
- 自定义分类（openai 之类）需要 geodata 模式加 GeoIP.dat，光改规则不生效。
- GEOSITE 按域名集合匹配，省掉手写清单，但只管域名。
- geodata 全量加载吃内存和启动时间，小内存设备上别同时跑两份。
- 数据有滞后，漏网靠兜底规则加手动补充。
