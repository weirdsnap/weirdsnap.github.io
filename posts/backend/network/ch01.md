# 一个数据包从手机出门要经过什么：NAT、转发与连接跟踪

这段时间在家里路由器上折腾分流，一开始总想着「规则写对了就行」，后来发现很多怪现象根本不在规则上，而在包还没走到规则那一层。于是回头把数据包的路径捋了一遍。这一篇讲最底层的两件事：路由器的转发是怎么发生的，NAT 又是怎么把内网地址换成公网地址的。

---

## 手机发出的包，第一站是网关

手机连着 Wi-Fi，地址大概是 192.168.5.23，网关写着 192.168.5.1。它访问 `example.com` 时先查 DNS 拿到 IP，比如 93.184.216.34，然后构造一个包：

```
源地址 192.168.5.23:51234
目标地址 93.184.216.34:443
目标 MAC  = 网关的 MAC
```

注意最后一行。手机并不知道公网路由怎么走，它只需要知道「这一步交给网关」，所以以太网帧的目的 MAC 是路由器的。这个包从无线接口进来，进入路由器的 bridge（桥），然后被送到 IP 层。

---

## 桥和路由不是一回事

这是很多人卡住的第一个点。路由器上有多个口：`lan1`、`lan2`、`wlan0`、`wan`。前三个通常和 CPU 内部的一个接口一起，被 `br-lan` 这个软件桥绑在一起。

桥做的事是二层交换：同一个桥里的口互相转发帧，不碰 IP 头。你手机访问 NAS，流量在桥里就转完了，根本不上 IP 层。

只有目标 MAC 是路由器自己（或者需要做三层转发）的时候，包才被交给 IP 协议栈。这一步的交接点叫 netfilter 的 `PREROUTING`。

所以一个路由器上同时存在两套转发：

- 二层桥转发：同一个子网内，看 MAC
- 三层路由转发：跨子网（内网到外网），看 IP 目的地址

内网访问外网属于第二种。而后者需要内核开一个开关：

```sh
cat /proc/sys/net/ipv4/ip_forward
```

如果是 `0`，内核会把「这不是给我的包」直接丢掉，哪怕路由表里写得好好的。OpenWrt 在防火墙启动时会把它设成 1。

---

## 路由决策发生在哪

包进 IP 层之后，内核查路由表（`ip route`），看到默认路由指向 `pppoe-wan`。于是确定出接口是 pppoe-wan。

但这时候还不能发出去，因为源地址是 192.168.5.23，是私有地址。公网上没有谁会给私有地址回包，所以必须在出门前换成公网地址。这件事就是 NAT。

---

## NAT 只做一次，靠连接跟踪记住

常见的写法是一条 iptables 规则：

```sh
iptables -t nat -A POSTROUTING -o pppoe-wan -j MASQUERADE
```

`POSTROUTING` 是包即将从网卡发出的最后一个钩子。`MASQUERADE` 的意思是「把源地址换成这个出接口的地址」。pppoe-wan 是动态获取的，所以用 MASQUERADE 而不是 SNAT 写死 IP。

关键点在于：这条规则不是每个包都执行的转换，而是只对「一条新连接的第一个包」做一次。做完之后，内核在连接跟踪表（conntrack）里记一条记录：

```
原始方向: 192.168.5.23:51234 -> 93.184.216.34:443
转换后  : 114.132.189.56:41201 -> 93.184.216.34:443
```

后续同一个连接里的所有包，都直接查表套用，不再走 nat 表。回包到达时，内核在 `PREROUTING` 之前先查 conntrack，发现这个包属于已知连接，于是自动把目标地址从 114.132.189.56:41201 换回 192.168.5.23:51234，再送进路由。

这解释了一件事：NAT 是有状态的。路由器重启，conntrack 清空，所有已经建立的连接全部断掉，哪怕对端还认为连接活着。我几次重启防火墙之后 SSH 卡住不动，就是这个原因：连接跟踪没了，回包找不到对应关系。

---

## 一条 NAT 记录能撑多少连接

公网 IP 只有一个，端口只有 65535 个，还要去掉系统保留的部分。所以「能同时开多少连接」是有上限的，大约六万多个。

现代浏览器一个页面能开几十条连接，加上各种 App 的心跳、视频分片，一两百条是常态。家里十几台设备加起来上千条也很正常。真正出问题的时候不是连接数不够，而是连接跟踪表本身满了：

```sh
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

表满之后新连接会被直接丢弃，日志里出现 `nf_conntrack: table full, dropping packet`。表现就是网突然卡一阵，过一会自己好了。

---

## 这条路和代理的关系

理解上面这些之后，代理的位置就清楚了：代理程序作为一个普通进程跑在路由器上，监听 7890 端口。手机把代理设成 192.168.5.1:7890，于是流量变成「手机到路由器上的一个进程」，再由这个进程对外发起新连接。

注意这里已经是两次完整的三层转发了：第一次是手机到代理，第二次是代理到外网。而代理那一段，还额外走了用户态。这一点下一篇再说。

---

## 小结

- 桥转发看 MAC，只在一个子网内；跨子网才上 IP 层，需要 `ip_forward`。
- 私有地址出门必须被 NAT 换掉，`MASQUERADE` 适合动态 IP 的拨号口。
- NAT 只对新连接的首包做转换，之后靠 conntrack 查表，所以是有状态、会丢的。
- conntrack 表大小决定了并发上限，满了就静默丢包。
