# 拷贝并交换惯用法（Copy-and-Swap）

实现 `operator=` 的现代 C++ 最佳实践：**按值传参隐式完成拷贝，与参数交换资源，让参数的析构函数自动释放旧资源**。一次写对，自赋值安全、强异常安全、移动赋值全部免费得到。

---

## 一、要解决什么问题

管理资源的类（裸指针、文件句柄、socket……）手写 `operator=` 时，直觉写法是"释放旧的 → 拷贝新的"：

```cpp
// ❌ 直觉写法，三个坑
NaiveBuffer& operator=(const NaiveBuffer& other) {
    delete[] data_;                    // 1. 释放旧资源
    size_ = other.size_;
    data_ = new char[size_ + 1];       // 2. 分配新资源
    std::strcpy(data_, other.data_);   // 3. 拷贝
    return *this;
}
```

### 坑 1：自赋值直接崩

`a = a` 时，`other` 就是 `*this` 自己。第 1 步 `delete[] data_` 把 `other.data_` 也一起释放了，第 3 步从悬垂指针拷贝。

AddressSanitizer 实测（`naive_assign.cpp`）：

```
ERROR: AddressSanitizer: strcpy-param-overlap:
memory ranges [0x602000000110,...) and [0x602000000110,...) overlap
    #1 NaiveBuffer::operator=(NaiveBuffer const&)
```

释放后 `new` 恰好复用了同一块地址，`strcpy` 的源和目标完全重叠——未定义行为。

### 坑 2：异常安全

第 2 步 `new` 失败抛 `std::bad_alloc` 时，旧资源已经在第 1 步释放，`data_` 成了悬垂指针。对象处于**已损坏状态**，之后析构还会二次释放。这连最基本的异常安全（basic guarantee）都不满足。

### 坑 3：拷贝赋值和移动赋值写两遍

`operator=(const T&)` 和 `operator=(T&&)` 的逻辑高度重复：都是"拿到 other 的资源，处理掉自己的旧资源"。

---

## 二、惯用法：三行解决

```cpp
class StringBuffer {
    char* data_;
    size_t size_;
public:
    // 成员 swap：交换内部资源，必须 noexcept
    void swap(StringBuffer& other) noexcept {
        std::swap(data_, other.data_);
        std::swap(size_, other.size_);
    }

    StringBuffer& operator=(StringBuffer other) {  // ① 按值传参
        swap(other);                               // ② 交换资源
        return *this;
    }                                              // ③ other 析构，带走旧资源
};
```

逐行拆解：

**① 按值传参 `StringBuffer other`**
调用 `a = b` 时，`other` 由 `b` **拷贝构造**而来——拷贝发生进入函数体**之前**。这一步把"复制资源"的职责完全移交给了拷贝构造函数，`operator=` 自己一行拷贝逻辑都不用写。

**② `swap(other)`**
`this` 和 `other` 交换内部指针。此刻：

- `this` 持有新资源的副本
- `other`（临时对象）持有 `this` 的**旧资源**

swap 只是交换几个指针/整数，不分配内存、不抛异常。

**③ 函数返回，`other` 析构**
临时对象离开作用域，它的析构函数 `delete[]` 掉旧资源。释放逻辑也不用写——复用了析构函数。

整个 `operator=` = 拷贝构造函数 + 析构函数 + 一个指针交换，**没有任何新代码路径**，这三个组件本来就都必须写且必须正确。

---

## 三、为什么三个坑同时消失

### 自赋值安全

`a = a`：`other` 是 `a` 的完整副本，`swap` 后 `a` 拿回一份内容相同的新内存，`other` 带着旧内存析构。全程没有悬垂指针，结果正确。代价是多了一次不必要的拷贝——但自赋值本就罕见，不值得为它加 `if (this == &other)` 分支（分支本身对每次赋值都是开销）。

### 强异常安全（strong guarantee）

异常安全分级：

| 级别 | 承诺 |
|------|------|
| 无保证 | 抛异常后对象可能损坏 |
| 基本保证 | 抛异常后对象仍处于有效状态（值可能改变） |
| **强保证** | 抛异常后对象**保持原值**，操作要么成功要么无效果 |
| 不抛保证 | 绝不抛异常（noexcept） |

Copy-and-Swap 里，唯一可能抛异常的是 ① 的拷贝构造（要分配内存）——它发生在 `*this` **被修改之前**。抛了？`this` 根本没动过，原值完好。进入函数体后只剩 noexcept 的 swap 和析构。天然强保证。

对比直觉写法：先 `delete[]` 再 `new`，异常点在对象已被修改**之后**，连基本保证都丢了。

### 移动赋值免费送

按值传参还有个隐藏福利：`operator=(StringBuffer other)` **一个函数同时是拷贝赋值和移动赋值**。

```cpp
a = b;                    // b 是左值 → other 拷贝构造
a = StringBuffer("tmp");  // 右值 → other 移动构造，零拷贝
a = std::move(b);         // 同上
```

参数 `other` 的构造按重载决议自动选择：左值走拷贝构造，右值走移动构造。传统方案要为两种赋值各写一个运算符，这里合一了。

---

## 四、swap 的要求

惯用法的全部正确性押在 `swap` 上，两条硬性要求：

1. **必须 `noexcept`**。swap 发生在"拷贝已成功"之后，如果它能抛异常，强保证就破了。成员指针/整数的交换天然不抛，直接标上。
2. **只交换成员，不分配资源**。逐成员 `std::swap` 即可。

标准约定还会提供一个**非成员** `swap` 友元函数，让 `std::swap`、ADL 和泛型算法能用上高效版本：

```cpp
friend void swap(StringBuffer& a, StringBuffer& b) noexcept {
    a.swap(b);
}
```

## 五、代价：什么时候不用它

惯用法不是免费的：

- **每次赋值必有一次完整拷贝**。即使 `this` 的现有容量足够复用（比如 `std::vector` 的 capacity 够大），也会从头分配新内存。
- 赋值大对象、且在热路径上时，这次分配可能不可接受。

不适合的场景：

- **性能敏感的频繁赋值**——比如容器内部元素的批量重排。标准库的 `vector`、`string` 都不用 copy-and-swap 实现 `operator=`，而是手写"能复用容量就复用"的逻辑，只保证基本异常安全。
- **成员很多且交换昂贵**的类——swap 本身变成开销。

判断标准很直接：**先保证正确性用 copy-and-swap，profile 证明赋值是热点后再手写优化版**。惯用法是默认答案，不是唯一答案。

## 延伸

- **Rule of Three / Five**：拷贝构造、拷贝赋值、析构三者需要其一则全需要；C++11 再加移动构造、移动赋值。Copy-and-Swap 让这五个函数的实现互相复用，几乎没有重复逻辑。
- **copy-and-swap 的泛化**："先做不可失败的准备，再一步提交"——事务式思维。`std::vector` 扩容也是这个模式：新内存全部构造成功后才替换旧内存。
- **C++23 的替代讨论**：有人主张用 `deducing this` 或默认实现进一步简化，但 copy-and-swap 至今仍是面试和代码审查里的标准答案。
