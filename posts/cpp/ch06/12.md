# 缓存行与伪共享

多线程程序里有一种性能陷阱：两个线程各写各的变量，没有任何数据竞争，代码评审看不出问题，但性能比单线程还差。原因是这两个变量恰好落在同一个缓存行里，这叫伪共享（false sharing）。要讲清楚它，得从缓存的结构说起。

## 一、缓存为什么按"行"搬运

存储层次的速度差是缓存存在的理由：

| 层级 | 访问延迟 | 容量 |
|---|---|---|
| 寄存器 | <1 ns | 几百字节 |
| L1 缓存 | ~1 ns | 每核 32–64 KB |
| L2 缓存 | ~3–10 ns | 每核 256KB–1MB |
| L3 缓存 | ~10–30 ns | 多核共享，几 MB 起 |
| 主存 DRAM | ~100 ns | GB 级 |

CPU 等一次主存要几百个周期，所以用 SRAM 缓存挡在中间。关键事实：缓存和主存之间不按字节搬运，按固定大小的块搬运，这一块就是缓存行（cache line），x86 和 ARM 上通常是 64 字节，Apple Silicon 是 128 字节。

按行搬的依据是空间局部性：程序访问了地址 X，大概率很快访问 X+1、X+2（遍历数组、顺序执行代码）。一次把整行搬上来，后续访问就免费命中。

## 二、缓存内部布局

以 32KB 的 L1 为例，它被切成 `32KB / 64B = 512` 行，每行长这样：

```
| 有效位 | 脏位 | 状态位(MESI) | 标签(tag) | 64 字节数据 |
```

内存地址被拆成三段来定位：

```
| tag（高位） | set 组号（中位） | 行内偏移（低 6 位） |
```

查找时先用中间几位定位到组（set），再在组内几个路（way）里比对 tag，命中后用低位取字节，这就是组相联结构。注意两点：

- 行按地址低位切分，`0x1000~0x103F` 永远在同一行，和变量的逻辑边界完全无关
- 每行的状态位是**整行共享**的，行内所有字节共用一个 MESI 状态

## 三、多核一致性也以行为单位

两个核各自有 L1，可能缓存了同一行的副本。核 0 改了其中一个字节，核 1 那份就成脏数据了。MESI 协议解决这个问题的粒度是整行：

- 核 0 要写某字节，先发 invalidate 消息，让核 1 把那整行标为 Invalid
- 核 1 再访问这行里任何字节，都会 miss，得重新从核 0 的缓存或主存拉整行

硬件不按字节做一致性，给每个字节维护状态位的开销是 64 倍，硅片面积和消息流量都承受不起。所以协议粒度等于搬运粒度，就是缓存行。

## 四、伪共享：两个抽象层级的错位

现在拼图齐了。看这段代码：

```cpp
struct Counters {
    std::atomic<long> a;   // 线程 1 疯狂写它
    std::atomic<long> b;   // 线程 2 疯狂写它
};
```

程序员的视角：两个独立变量，两个线程各用各的，连锁都不用（atomic 保证无数据竞争）。

硬件的视角：`a` 和 `b` 在同一个 64 字节缓存行里，共用一个 MESI 状态位。于是：

- 线程 1 写 `a`，核 1 上整行失效（包括 `b`）
- 线程 2 写 `b`，核 0 上整行失效（包括 `a`）
- 两个核互相 invalidate，缓存在核间来回弹跳，每次写都要等缓存行所有权转移

逻辑上零共享，物理上每写必冲突。这就是伪共享。它阴险在代码层面完全看不出来，要靠 perf 看 cache-misses / HITM（hit modified）计数才能抓到。

## 五、实测（Apple Silicon，g++-14，-O2）

两个线程各对各自的 `std::atomic<long>` 做 1 亿次 `fetch_add(relaxed)`：

```cpp
struct Packed {                    // 挤在同一缓存行
    std::atomic<long> a{0};
    std::atomic<long> b{0};
};

struct alignas(std::hardware_destructive_interference_size) AlignedCounter {
    std::atomic<long> v{0};
};
struct Padded {                    // 各占一个缓存行
    AlignedCounter a;
    AlignedCounter b;
};

double run(std::atomic<long>& a, std::atomic<long>& b) {
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1([&] { for (long i = 0; i < 100'000'000; ++i)
        a.fetch_add(1, std::memory_order_relaxed); });
    std::thread t2([&] { for (long i = 0; i < 100'000'000; ++i)
        b.fetch_add(1, std::memory_order_relaxed); });
    t1.join(); t2.join();
    return std::chrono::duration<double>(
        std::chrono::steady_clock::now() - t0).count();
}
```

结果：

| 布局 | 耗时 |
|---|---|
| packed（同一缓存行） | 0.68 ~ 0.72 s |
| padded（各占一行） | 0.16 s |
| **差距** | **4.2 ~ 4.5x** |

## 六、解决办法

让频繁被不同线程写的变量各占一个缓存行：

```cpp
// 手动填充
struct PaddedManual {
    std::atomic<long> a;
    alignas(64) char pad[64];      // 把 b 顶到下一行
    std::atomic<long> b;
};

// C++17 起用标准常量，不用自己猜行宽
struct alignas(std::hardware_destructive_interference_size) Counter {
    std::atomic<long> v;
};
```

其他语言也有对应机制：Java 的 `@Contended` 注解，JDK 的 `LongAdder` 用分段 Cell 数组替代单个 `AtomicLong`，就是为躲这个问题设计的。无锁队列里头指针和尾指针也要隔开，它们分别被生产者和消费者写。

典型踩坑场景：线程池的 per-thread 计数器、分桶哈希的桶锁。结构上按线程分槽（`counter[thread_id]`），比共享字段好。

## 七、布局原则：访问者局部性

空间局部性这个词有误导性。缓存行机制赌的其实是：**相邻数据会被同一个核在相近时间访问**。缓存是每个核的私有资源，优化的目标是每个核的命中率，所以数据布局要匹配单个核的访问模式：

- 空间相邻且被同核访问，真局部性
- 空间相邻但跨核访问，负局部性（伪共享）

同一行里的数据，要么一起被同一个核用，要么干脆别放同一行。缓存行应该对齐访问权的边界，而不是逻辑数据的边界。由此推出两种方向相反、原理相同的操作：

**该分的分**（为不同核拆开访问权）：per-thread 计数器按行宽对齐、分桶锁、percpu 变量、TLS。

**该聚的聚**（为单核访问聚合同行数据）：结构体热字段放前面冷字段挪后面（hot/cold splitting）、SoA 替代 AoS（遍历所有实体的 x 坐标时，每行都装满纯坐标，不浪费在 y、z、name 上）。

伪共享和 AoS/SoA 优化看似方向相反，其实是同一件事的两面：让缓存行的内容和它的访问者对得上。
