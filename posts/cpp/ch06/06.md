# std::atomic 内存序

原子操作保证"这一下不会被打断"，但不保证"别人按什么顺序看到"。后者由内存序（memory order）控制。

## 问题从哪来：两层重排

你写的代码顺序，不等于实际执行的顺序：

- **编译器**为了优化，会把没有依赖关系的读写换顺序。
- **CPU** 更狠：写先进 store buffer，读可以乱序发射，多核各自的缓存同步还要时间。

单线程看不出来，as-if 规则兜底（重排不许改变单线程可观察结果）。多线程就露馅了：

```cpp
std::atomic<bool> flag{false};
int data = 0;

// 线程 1（写）                // 线程 2（读）
data = 42;                     while (!flag.load());
flag.store(true);              print(data);  // 可能打印 0
```

线程 1 明明先写 `data` 再置 `flag`，线程 2 却可能看到 `flag` 是 true 而 `data` 还是旧值。两个写被换了序，或者 `flag` 的新值先一步同步到了对方的缓存。

## 锁为什么让你不用想这个

之前用 `mutex` 时从没碰过这个问题，因为锁自带内存序：

- `unlock()` 是 **release**：临界区里的所有写，不许重排到 unlock 之后。
- `lock()` 是 **acquire**：拿到锁之后的所有读，不许重排到 lock 之前。

前一个线程在临界区写的一切，对后一个拿到锁的线程完整可见。无锁编程没人替你兜这个底，就得自己指定内存序。

## 记住三档就够

六种内存序里，日常只用三档：

- **`relaxed`**：只保证原子性，不管顺序。计数器专用，加一就行，不关心别的操作谁先谁后。
- **`release` / `acquire` 配对**：工作主力。记成"发布与订阅"：写方 release 喊一声"我东西都摆好了"，读方 acquire 拿到这声之后才动手，写方此前的所有写对它可见。
- **`seq_cst`**（默认）：全局统一顺序。最省心也最贵，x86 上 store 要刷 store buffer。拿不准就用它，对了再降。

上面的例子改成这样就对了：

```cpp
// 线程 1（写）                                   // 线程 2（读）
data = 42;                                       while (!flag.load(std::memory_order_acquire));
flag.store(true, std::memory_order_release);     print(data);  // 保证是 42
```

口诀：**写方 release，读方 acquire，同一个变量，配对才管用**。单独一个 release 或单独一个 acquire 什么都不保证。配对成立时，两线程之间形成 happens-before：写方 release 之前发生的所有写，都"发生"在读方 acquire 之后的所有读之前。

## 实战：环形缓冲区的下标

无锁 ring buffer 就是 message passing 换层皮，下标是标志位，数据是 payload：

```cpp
// push（生产者）
buffer[tail % N] = x;                              // 先写数据
tail.store(tail + 1, std::memory_order_release);   // 再发布下标

// pop（消费者）
auto t = tail.load(std::memory_order_acquire);     // 先拿下标
auto x = buffer[t % N];                            // 再读数据，保证读到新值
```

消费者看到新 tail，就一定能看到新数据。全写成默认的 `seq_cst` 也对，只是白付性能。完整实现见延伸的环形缓冲区一篇。

## 六档全表（备查）

| 内存序 | 语义 | 适用场景 |
|--------|------|----------|
| `relaxed` | 无顺序约束 | 纯计数器 |
| `acquire` | 读不许提前 | 读标志、lock |
| `release` | 写不许延后 | 写标志、unlock |
| `acq_rel` | acquire + release | 读改写一体（CAS、fetch_add 要同步时） |
| `consume` | 数据依赖版 acquire | 标准自己没整明白，别用 |
| `seq_cst` | 全局统一顺序 | 默认，最强也最慢 |

## 常见误区

- ❌ `relaxed` 能保证其他线程看到最新值：片面。`relaxed` 只保证单个变量的修改是原子的，不管顺序也不管别的变量的可见性。
- ❌ `acquire` 和 `release` 可以单独使用：错误。必须配对作用于同一个变量，才能建立 happens-before。
- ❌ 内存序管的是变量本身：错误。内存序管的是这个原子操作"周围"的非原子读写能不能越过它，标志位保护的是旁边的普通数据。
- ❌ 原子操作越多越安全：错误。每个原子操作都对了，组合起来照样错，见数据竞争一篇。
