# std::function 类型擦除

`std::function` 能用一个类型装下函数指针、lambda、仿函数，靠的是**类型擦除**（type erasure）：用一个固定的静态类型包装各种具体类型，把"具体是什么"藏起来，只留下"能干什么"的接口。擦除擦的是类型信息，不是数据。

## 三段式骨架

所有类型擦除设施都是同一个结构：

```cpp
// ① 非模板基类：只描述"能做什么"
struct Concept {
    virtual void call() = 0;
    virtual ~Concept() = default;
};

// ② 模板壳子：实例化时知道真实类型，由编译器生成
template<class T>
struct Model : Concept {
    T fn;
    void call() override { fn(); }
};

// ③ 持有者：类型固定，眼里只有 Concept
struct Func {
    std::unique_ptr<Concept> p;
    template<class T> Func(T f) : p(std::make_unique<Model<T>>(std::move(f))) {}
    void operator()() { p->call(); }
};
```

关键设计：**构造函数是模板**（在类型还可见的地方捕获具体类型），**类本身不是模板**（之后类型就消失了）。`std::function`、`std::any`、`shared_ptr` 的控制块，都是这个模式。

## 开销从哪来

类型擦除的代价就在这三层结构里：

- **间接调用**：调用要过虚表，编译器在使用点看不到具体类型，无法内联。模板调用能把整个调用内联优化掉，擦除后这条路断了。
- **堆分配**：`sizeof(std::function<void()>)` 在 GCC 和 Clang 的 64 位实现下都是 32 字节，里面有一小块内联缓冲区（SBO），装不下的可调用对象（比如捕获了大数组的 lambda）就堆分配。
- **体积**：持有者至少要存对象指针加操作表指针，比裸的可调用对象大。

SBO（Small Buffer Optimization）是缓解手段：小对象直接放进 `std::function` 内部的缓冲区，不触发堆分配。但只要对象超过缓冲大小（或不可拷贝进缓冲），就回到堆上。

## 和模板的对照

| | 模板（类型保留） | 类型擦除 |
|---|---|---|
| 类型信息 | 编译期全保留 | 使用点被擦除 |
| 代码生成 | 每个类型一份 | 一份服务所有类型 |
| 内联 | 可以 | 不能 |
| 异构容器 | ❌ | ✅ |
| 二进制体积 | 膨胀 | 小 |

两者是取舍关系：要性能、要编译期检查走模板；要统一类型、要装异构容器（`vector<function<void()>>` 放一百种 lambda）、要稳定 ABI，走类型擦除。

顺带一个视角：虚函数本身就是 C++ 最原始的类型擦除。`Base*` 看不到子类具体是谁，只知道"能调什么"。`std::function` 无非是把这套机制用模板自动化了。

## 删除器是同一个故事

这个模式解释了智能指针删除器的差异：

- `unique_ptr` 的删除器是模板参数，**类型保留**：编译期确定，无状态删除器零开销；代价是删除器换了类型就换了。
- `shared_ptr` 的删除器存进控制块，**类型擦除**：构造函数是模板，生成一个知道具体删除器类型的控制块子类，`shared_ptr` 本身只看到非模板基类。所以什么删除器都是 `shared_ptr<T>`，代价是控制块分配和一次间接调用。

详见 [unique_ptr vs shared_ptr](./blog.html?post=cpp/ch03/04.md)。

## 常见误区

- ❌ `std::function` 和函数指针一样快：错误。多一层间接分派，且无法内联；对象大了还有堆分配。
- ❌ 空 `std::function` 调用是 UB：错误。调用空 `std::function` 抛 `std::bad_function_call`。
- ❌ 类型擦除就是"万能指针 `void*`"：`void*` 只存地址不带操作，恢复类型靠程序员自己保证；类型擦除带着操作表，恢复和调用是类型安全的。
