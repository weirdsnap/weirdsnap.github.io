# shared_ptr

`shared_ptr` 通过控制块管理引用计数，支持自定义删除器；引用计数操作线程安全，但对象本身非线程安全。

## 控制块与对象

shared_ptr 管理的其实是两段东西：

- **对象**：你 `new` 出来的那个 T。
- **控制块**：堆上的一块管理数据，里面是强引用计数、弱引用计数、删除器和分配器。

每个 shared_ptr 实例里存的是对象指针加控制块指针两个值，所以 `sizeof` 是裸指针的两倍。

销毁分两步，别合成一句"计数归零就释放"：

- 强计数归零：调用对象的析构函数。注意这一步只是析构，内存不一定归还。
- 弱计数也归零：控制块才销毁。`weak_ptr` 的 `lock()`、`expired()` 要读控制块里的计数状态，所以只要还有 weak_ptr 活着，控制块就必须活着。

## 计数变化

| 操作 | shared_count | 说明 |
|------|-------------|------|
| 构造 | +1 | 初始化为 1 |
| 拷贝 | +1 | 共享所有权 |
| 移动 | 不变 | 转移所有权 |
| 析构 | -1 | 归零时析构对象 |

## make_shared vs new

`make_shared<T>(...)` 把对象和控制块**合并成一次堆分配**；`shared_ptr<T>(new T)` 是两次，对象一次、控制块一次。合并的好处：

- 少一次堆分配。
- 对象和控制块内存相邻，缓存友好。

代价是内存释放变晚：两段焊在同一块内存里，就算强计数归零、对象已析构，只要还有 weak_ptr 活着，整块内存都不能归还。所以准确的说法是 **weak_ptr 钉住的是对象所在的那块内存**。对象大且 weak_ptr 长寿的场景要掂量这个。

`new` 版本还有个历史坑：

```cpp
f(std::shared_ptr<A>(new A), g());
```

C++17 之前参数求值顺序不保证，可能 `new A` 先执行、shared_ptr 还没接管、`g()` 抛异常，裸指针就泄漏了。make_shared 一步完成分配和接管，没有这个问题。C++17 起函数参数之间禁止交错求值，坑没了，但 make_shared 仍是默认推荐。

不用 make_shared 的情况：

- 需要自定义删除器（make_shared 不接受删除器参数，它自己安排分配和销毁）。
- 接管已有的裸指针（比如 C API 返回的）。
- 上面说的大对象加长寿 weak_ptr。

## 线程安全的三层

这是最容易答混的地方，要分三层说：

- **计数的增减是原子的**：多个线程各持一份拷贝（不同实例）是安全的。
- **指向的对象不是线程安全的**：并发读写对象内容要自己同步。
- **同一个 shared_ptr 实例的并发读写也是数据竞争**：一个线程 `reset`、另一个线程读这个变量本身，不行。需要时用 `std::atomic_load` / `std::atomic_store` 自由函数，C++20 起有 `std::atomic<shared_ptr>`。

## 常见误区

- ❌ `shared_ptr` 线程安全所以可以多线程无锁读写同一对象 — 错误，见上面三层。
- ❌ 用 `this` 构造新的 `shared_ptr` — 错误。两个 shared_ptr 各自接管同一裸指针，会建出两个控制块，各自计到零，重复释放：

```cpp
A* p = new A;
std::shared_ptr<A> s1(p);
std::shared_ptr<A> s2(p);  // 第二个控制块，double free
```

类内部需要拿自己的 shared_ptr，继承 `std::enable_shared_from_this`，原理是对象内部存一个 weak_ptr，第一个 shared_ptr 接管时回填。注意构造函数里不能调 `shared_from_this()`，那时控制块还没建好。
